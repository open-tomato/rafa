Blocked by: #23

## What you get

`rafa effort report --skills` shows, for each skill and each lesson, whether it is earning its place, being ignored, or being used while the failure it should prevent keeps recurring. It reads over one plan or over several. The report shows co-occurrence and flags recurrence, and says so in its header: without a control, no line claims a cause. When a plan ran under more than one of #23's resolvers, the tables are split by resolver, which is the reading #23's measurement protocol needs.

## Starting position

- **From #23:**
  - each dispatch records `resolver`, `skills_offered` and `lessons_offered`;
  - `skill_invocations` counts `Skill` calls per session, in the main thread and in sidechains;
  - `SKILL_USE_CLI_VERSION` is pinned.
- **Task outcome** is in `task_reports.outcome` (`done` or `blocked`).
- **What the report parser reads but nothing stores:** `skills_used`, parsed into `TaskReport.skillsUsed` (`src/report/parse.ts`).
- **Failure text rafa already stores:** findings (`trigger`, `what`, `cause`, `artifact`), `blockers` and `out_of_scope_bugs`, in `.rafa/effort/effort.sqlite`.
- **CI is read, but not recorded per plan.** `pr triage` and `pr merge` read a pull request's checks (`src/pr/*`), and the effort store keeps no CI verdict.
- **Skills name what they prevent only in prose.** The frontmatter `prevents` and `signal` fields (`src/schema/skill.ts`) are text. Nothing can match them. The instinct's `artifact` is documented as "the recurrence key".
- **`rafa effort report` today has** a group table, task report tallies, preflight halts and budgets (`src/effort/report.ts`, `report-format.ts`).
- **Claude Code's own view.** `/skill-doctor` reports skill usage. Where the CLI keeps those counts has not been measured.

## Design

### A fact row per task (a view, not a table)

For each task session: plan, task line, resolver, skills offered, skills invoked, skills reported (`skills_used`), lessons injected, outcome, the plan's CI verdict, and the failure strings that recurred.

### Storage

- `task_reports` gains `skills_used` (JSON).
- A new SQLite-only table `plan_ci(plan_stub, pr, head_sha, verdict, failing, read_at)` is written whenever `pr triage` or `pr merge` reads checks:
  - `verdict` is `green`, `red` or `none`;
  - `failing` holds the names of the failing checks.
- The CI verdict belongs to the plan and is labelled "plan CI" everywhere. It is never attributed to a single task.

### Failure strings and recurrence

- **Skills can declare what their failure looks like.** A skill may declare `failure_strings:`, a list of literal strings such as `TS2769` or `no changes added to commit`, as a new optional frontmatter field. The checker refuses an empty string and warns on one shorter than 6 characters.
- **For a lesson, the failure string is its `artifact`.**
- **What counts as a recurrence.** A failure string that appears, as a case-sensitive literal, in any of:
  - the task's findings, blockers or out-of-scope bugs;
  - a later task's findings, blockers or out-of-scope bugs in the same plan;
  - the names of the plan's failing CI checks.
- **Only text rafa already stores is searched.** Session transcripts are never searched, which keeps `session-log.ts`'s stance.

### The signals, defined once in `src/effort/skill-signals.ts`

- **Skills.** Each skill falls into exactly one of these, checked in this order:
  1. **`recurring`**: invoked in a task where one of its failure strings then recurred.
  2. **`unmeasured`**: invoked, but it declares no `failure_strings`. Printed as `invoked N/M, recurrence not declared`.
  3. **`earning`**: offered and invoked in at least one task, with no recurrence after any invocation.
  4. **`ignored`**: offered in at least one task and invoked in none.

  Also listed, with no signal: skills invoked but never offered.
- **Lessons.** A lesson cannot be observed being applied, because no tool call marks it. It gets one of:
  - **`injected-recurring`**: its `artifact` recurred after it was injected;
  - **`injected`**: no recurrence.

  "Ignored" is not claimed for a lesson.
- **Two readings of use.** `skills_used` (what the session says it used) and invocations (what the log shows) are two columns, never merged. The signals read invocations.

### Agreeing with Claude Code's count

- "Invoked" means what Claude Code counts as a use of a skill. A probe is the plan's first task:
  1. Record one session that invokes two skills.
  2. Find where the pinned CLI keeps per-skill usage (the source `/skill-doctor` reads).
  3. Compare it with `skill_invocations` for that session.
- A match is a test. A difference is written into `context/effort-store.md` with its reason, and the report's footnote names it.
- Names are normalised the way #26 serves them: `plugin:name` is kept, and served rafa skills use their bare names.

### The report

- **`rafa effort report --skills [--plan=<stub>] [--json]`** has two parts:
  - one table per skill: offered, invoked, reported, tasks with a recurrence, signal;
  - one table per lesson.
- **Its header is fixed text:** `Co-occurrence, not cause: a skill can be invoked and its failure recur for reasons the skill does not cover.`
- **Plans that ran under several resolvers** get tables split by resolver, including #23's M1 and M2.
- **`--json`** follows a documented schema, and a test checks it.

### #118

No new setting. The signal definitions are code, not policy. A project that wants a different reading writes its own report from `--json`.

## What can go wrong

- **A failure string is too generic and recurs everywhere.** The checker warns on strings under 6 characters. The report lists which text matched, so an over-broad string shows up in the first reading.
- **A session reports a skill it never invoked, or the reverse.** Both columns are shown. Only invocations drive the signals.
- **A red CI verdict is read as one task's fault.** It is labelled plan CI and never counted per task.
- **The report is read as proof that a skill works.** The header states co-occurrence. `earning` means only that no recurrence was seen.
- **Claude Code changes where it counts usage.** `SKILL_USE_CLI_VERSION` catches it with a `doctor` row, and the probe is re-run.
- **A plan with no offers**, run under resolver `none`, reports every skill as `invoked but never offered`, which is correct for a baseline.

## Tasks the plan must carry

- The probe comparing Claude Code's usage record with `skill_invocations`, recorded in `context/effort-store.md`.
- `task_reports.skills_used` and `plan_ci`, each a migration with the table-list expectations updated. The `plan_ci` writers in `pr triage` and `pr merge`.
- `failure_strings` in the skill schema and checker.
- The recurrence matcher over stored findings, blockers, out-of-scope bugs and check names.
- `src/effort/skill-signals.ts` with a fixture for each skill signal and each lesson signal.
- `--skills`, `--plan=` and `--json` on `rafa effort report`, with the fixed header and the per-resolver split.
- Documentation: `context/effort-store.md`, the README section on effort, help snapshots, and `describe`.
- `changes:` notes and `release: minor`. Tick the README Roadmap line "Know which skills earn their place".

## Definition of done

- A fixture plan runs under the stand-in `claude`, with recorded session logs and one full plan's reports. There, `rafa effort report --skills --plan=<stub>` shows:
  - skill A, offered and invoked with no recurrence, as `earning`;
  - skill B, offered and never invoked, as `ignored`;
  - skill C, invoked while its failure string appears in a later task's blocker, as `recurring`;
  - a skill with no `failure_strings` as `unmeasured`.
- A lesson whose `artifact` appears in a failing check name after it was injected is `injected-recurring`.
- `--json` matches the documented schema, and the header line is present in the text output.
- The probe's recorded session gives the same count from `skill_invocations` as from Claude Code's own usage record, or `context/effort-store.md` names the difference and why.
- A plan run half under `planner` and half under `tag` prints tables split by resolver, including M1 and M2.
