Consent: no unit of this cluster asks a question. The cluster has no prompter, no `--yes` and no `--dry-run`; the one decision a person gives in advance is `--accept-unchecked`, which is a flag read by `readCloseLine` through `readSwitch`. `epic close` is nevertheless the one command here that spends Claude sessions and closes an issue, and it refuses rather than asks.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **`rafa epic close`:** the line (`readCloseLine`) → the board listing read once → `readEpicToClose` (labels or native members) → `splitCriteria` → one planning session (`planVerification`, none when every criterion is a placeholder) → uncheckable criteria named and refused unless `--accept-unchecked` → `runVerification` (flow 2) → each verdict read, each failure filed through `triageReport` (flow 4) → `closeWithComment` closes as completed with `renderCloseComment` → `readEpicCost` printed beside the estimate. `closeEpic` and `runEpicClose` in `src/commands/epic/close.ts`; it ends json mode with an `EpicCloseResult`.
2. **The verification run:** `git fetch origin` → `git rev-parse --verify origin/main^{commit}` → `git worktree add --detach <home>/.rafa/worktrees/epic-<n> <commit>` → one captured session per check, each ending in a `rafa:verdict` block → `git worktree remove --force` in a `finally`. `runVerification` in `src/epic/verify-run.ts`; each git step is a `VerifyGitStep` and each answer a `VerifyGitOutcome`.
3. **The tracker chain:** `tracker.default` then `tracker.fallback`, each kind made through the adapter registry → its `preflight` → the first that answers ok lands, with every failure joined into the `fallbackReason` it was made with → the `local` adapter writes that reason into each issue file it creates. `resolveTracker` in `src/adapters/tracker/resolve.ts`, `createLocalTracker` in `local.ts`; the registry is `src/adapters/registry.ts` (`c03-config`).
4. **One report's triage in a loop run:** `parseReport` over the task's output → blocker text written onto the task's line → each out-of-scope bug routed (machine, private, public) → a public one looked up (stored reference, `find` by key, nearest open bug), its state read, then filed, superseded or commented on → the reference stored → one line per outcome through the active output and one `inherited` loop event per inherited failure. `createStartTriage` in `src/start/triage.ts`, `triageReport` in `src/triage/triage.ts`; the same `triageReport` is flow 1's filing step.
5. **`rafa issue create`:** `expectNoArgument` and the flags read into a draft → `--body-file` read → a spec's `Blocked by:` line read (`readSpecLine`) → the chain resolved → the board's numbers listed and the line settled (`settleSpecLine`) → `tracker.create` → the ref, its URL and any warning written. `createIssue` in `src/commands/issue/create.ts`.
6. **`rafa issue show`, `comment`, `move`:** the line → the chain → one `get`, `comment` or `transition` on the ref the id names → text lines or the result event. `showIssue`, `commentOnIssue` and `moveIssue`, each over `resolveIssueTracker` of `c01-github`.
7. **A tracker adapter's contract:** `runTrackerContract` registers every case of `trackerContractCases` against a fresh adapter; `contract.test.ts` runs the list against broken adapters to hold that each case can fail. `src/adapters/tracker/contract.ts`, called from the `local`, `github` and registry tests.

## Cut order this implies

The cluster has three lines through it that a cut can use.
