### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **The wrap-up's release stage:** `resolveReleaseEnabled` → `prepareRelease` fetches the base, reads the fragments waiting on it, allocates a name and writes the plan's fragment → the wrap-up session rewrites its notes (outside) → the loop's checkout guard → `verifyRelease` (restores step 1's bytes on a refusal) → commit of the one path → push → `readBranchForecast` and `releaseBodyBlock` → `carryReleaseIntoPullRequest` writes the forecast or the failure sentence into the pull request body (a second chance when no pull request was open). `src/start/release-stage.ts` (`prepareReleaseStage`, `finishRelease`), `release/prepare.ts`, `verify.ts`, `branch-forecast.ts`, `start/release-body.ts`; the caller is `src/start/wrap-up-run.ts` (`c02-active`), so the flow crosses the boundary twice.
2. **`rafa release settle`:** project and config → the provider when `release.settle: pr` and not a dry run → `withSettleWorktree` fetches and adds a detached worktree → `readSettle` (fragments in first-parent order, the version at that commit, the fold) → `buildSettle` writes the version, the section, deletes the folded fragments and commits `chore: release <version>` → `settleByPush` (one retry on a race) or `settleByPr` → `tagSettle` → the worktree removed. `src/commands/release/settle.ts` (`runSettle`), `src/release/settle*.ts`, `strategy.ts`, `fragment-tree.ts`, `changelog.ts`, `version.ts`.
3. **`rafa release tag`:** the branch, the version file, the tags, the changelog's newest section, the receipt, the commit that set the version → `decideTag` (six refusals) → `git tag` → the publish and push lines, or `pushTag` with `--push`. `src/commands/release/tag.ts` (`readTagInputs`, `decideTag`, `runTag`), `release-commit.ts`, `release/receipt.ts`, `tag-push.ts`.
4. **`rafa release status`:** the version file, the tag list, the untagged versions, the pending notes for the plan (from the store), the waiting fragments with their settle forecast, the audit → one block, text or json; each reading that fails is a `?` cell. `src/commands/release/status.ts` (`readStatus`, `renderStatus`), `status-fragments.ts`, `release/audit.ts`.
5. **The release guard in `rafa pr merge`:** `resolveReleaseEnabled` → fetch the base and the head (a failed fetch is a note) → `readGuard` (merge base, the stamp, the base's entry, the branch's fragments, the forecast, the local level report) → `guardReaction` → silent, print, report, ask, refuse or accept → the merge, then `cleanUpAfterMerge` and the follow-ups, among them the settle line when the dry run folds fragments. `src/commands/pr/merge-guard.ts` (`guardBeforeMerge`), `src/release/guard-merge.ts`, `guard.ts`, `commands/pr/merge-cleanup.ts`; `merge.ts` (`c06-command`) decides when each runs.
6. **The version conflict in `rafa pr triage`:** `readTriageGuard` (no fetch) → `classifyTriage` → `conflict-version` → `convertStampedVersion` (fetch, guard, the three files, one commit) → the caller adds and removes the worktree and pushes. `src/commands/pr/triage-guard.ts`, `src/pr/triage/version-convert.ts`; the caller is `src/commands/pr/triage-convert.ts` (`c07-index`).
7. **The forecast column of `rafa pr list`:** `readBodyForecast` over each open pull request's body → `createBaseReader` reads the base now → `forecastMoved` marks `(base moved)` or `(base ?)` → one cell and one explanatory line. `src/commands/pr/list-forecast.ts`, `src/release/body-forecast.ts`, `forecast.ts`.

## Cut order this implies

The cluster has one line through it that a cut can use and two it cannot. The line is the release package itself: `src/release/` with `src/commands/release/`, `src/start/release-stage.ts` and `release-body.ts`, `src/pr/triage/version-convert.ts` and `src/config-readers.ts`. It takes 92 edges and is called through 35, mostly at three files (gaps 9 and 11); only the cycle of gap 8 and the utility of gap 12 stand in its way, and both are small. The two lines it cannot use are the config (gap 7: the section file and the readers are `c03-config`'s to release) and the `pr` commands that own the guard's callers (gap 10), which belong to the `pr` package and stay.

Taken first, gap 8 (the changelog and version readers out of `src/commands/release/status.ts` into a leaf under `src/release/`) and gap 12 (`errorCode`), because they are within the cluster and take no other package to exist; then the section (gap 7), with `src/config-readers.ts` and `src/config-schema-release.ts` together, since the release's keys have their file already. Then the stage as the first steps (gap 4), the nearest to the contract of anything in this cluster and the one the loop calls by name, and settle with its dry run (gaps 5 and 6) as the first flow with a swap that already has a real `--dry-run`; the guard's `ask` (gap 3) comes with the stage because both are read by the same two callers. Taken last, the guard's callers in `pr merge` and `pr triage` (gaps 10 and 11) and the fixtures (gap 13), which wait on the `pr` package and the loop package to exist; the three commands (gap 1) move with the package, together.
