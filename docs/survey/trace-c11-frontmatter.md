### Commands

All four satisfy the superset shape `commandProblem` checks (`subject`, `action`, `summary`, `flags`, `examples`, `outputs`); one, `skill backfill`, declares `spends`. Things a package has to take on:

- The `RafaCommand` type, `RafaContext` and `CommandExit` are in `c06-command` (`src/cli/command.ts`, line 184 for `run`); every edge from this cluster into it is that one file.
- `check-report.ts` is where the two checks are one: they differ in the `CheckKind`, the usage line and whether `--fix` and `--project` are on the line, so the runner is written once and each command is its declaration plus `checkCommandRun`. It reads the flags before the directory, because `parseArgs` gives `--fix` the next word as its value; that order is part of the command's refusals and a package keeps it.
- On a failing run the report is the message of the `CommandExit` and not a result payload, because the dispatcher drops a nonzero exit's `result`; a clean run gives the reports as the data of the terminal event. The contract's `{ outcome, context?, message? }` has to carry the same split.
- Neither check resolves a project (`needsProject: false`), so a user tier at `~/.claude/skills` is checked with no project; `skill demote` and `skill backfill` do resolve one, only for its `home` and `root`.

### Steps with guards

Nothing here is a registered step. These are the units the cluster contributes to a command, with the guard that decides each and the class #119's vocabulary would give it. The classes are an assignment from `docs/workflow-checks.md` §6 and the source; no code declares them. "Behaviour" means no setting or flag turns the refusal off.

| Step (today's unit) | File | Guard that decides it | Class |

| apply reviewed proposals | `src/backfill/propose.ts` (`applyProposals`, `fileRefusal`), `proposal-file.ts` | a file marked `draft`, one naming another skills directory and a row whose sha256 changed are refused; an unanswered row is passed over untouched | 🔒 and 🧭 |

No class is ⚠️: no `dangerous.*` key is read here, so no guard needs a `passedBy`. The 🧭 class is the review, and it is held in a file, not in the context.

Consent: the cluster has the survey's second kind of typed answer and the first that is durable. `rafa cleanup` in `c05-sessions` asks a person at a prompt; here the answer is a person editing a file. `<scope>/.rafa/demoted/report.md` and `<scope>/.rafa/backfill/proposals-<nn>.yaml` carry `status: draft` until a reviewer marks them `reviewed`, with a sha256 per row that ties the consent to the bytes the reviewer saw, and `--apply` refuses a draft whole. It survives a session, is per row (an override is carried only when the hash still agrees), and is invalidated by a change of the set. Nothing of it is in the context: a package that wants the contract's `ctx.answered` has to read the file into the context before the step runs, and keep the file as the audit trail. Without `--apply` the demotion run is the nearest thing to `--dry-run` here, and `skill backfill` with no flag is the other; each is a mode of the command and not a flag the contract could pass down to a step.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions and files with a refusal or a review between steps and no flow declaration.

1. **Check a tier:** `scanLayout` walks the directory and reads each entry's kind (a broken symlink is `unreadable-entry`, not skipped) → each file is opened once → layout, schema (or the instinct schema), resolution and locality stages run in `CHECK_STAGES` order and are stable-sorted by stage → the failing entries are counted, capped at 255 → with `--fix`, a file whose only failures are a missing `tags` or `stack` is rewritten and re-checked. `src/commands/skill/check.ts` and `instinct/check.ts` over `check-report.ts`, `src/check/run.ts` and `layout.ts`; `references.ts` (`c03-config`) answers the two body stages.
2. **The demotion pass:** `resolveDemotionScope` from the directory and the home → `selectSources` (every `<name>/SKILL.md`, and the `learned/` files by `origin`) → `classifySkill` per file → `buildDemotionReport` carries a previous review over where the hashes agree → `report.md` written, nothing moved → a person edits and marks it `reviewed` → `--apply` parses it (a half-finished review parses to null) → `planDemotion` converts each observation to an instinct and checks it in a scratch directory → `applyDemotion` writes `<base>/.rafa/instincts/<id>.md` and moves the original to `<base>/.rafa/demoted/` → `rafa instinct check` over what was written. `src/commands/skill/demote.ts`, `src/demote/{select,classify,draft,report,apply}.ts`; `tests/demotion-pass.test.ts` drives it end to end.
3. **The backfill:** no flag, `planDerivation` reports what would be written and how many files a session would be asked about → `--propose` selects candidates by need (`prevents`, `trigger`, `description`), runs one session per batch of 20 and writes `proposals-<nn>.yaml` as `draft` → a person corrects, answers and marks each `reviewed` → `--apply` backs up every file outside the checkout, writes the reviewed rows, then runs the derivation (in that order, because `when_to_use` is built from the `prevents` the proposals wrote), re-checks each file and restores any that came out worse. `src/commands/skill/backfill.ts`, `src/backfill/*.ts`, with the session through `src/utils/claude.ts` (`c02-active`).
4. **A tier from untouched to clean:** `rafa skill check --fix` → `skill backfill --propose` → review → `skill backfill --apply` → `rafa skill check` at exit 0 with no `--fix`. Flows 1 and 3 in the order a person runs them; `src/tests/backfill-pipeline.test.ts` drives it with a stand-in `claude` first on `PATH`.

## Gaps

Every export that is missing or partial, with the file a cut would have to change. Gaps 1 to 3 are the contract itself and would be the same for any cluster; gaps 4 to 14 are specific to this one.

A cut changes `src/cli/command.ts` (the type), the four files under *Registered commands*, `src/commands/check-report.ts` (which carries the shared runner and its `CommandExit` refusals) and the import lines in `src/commands/index.ts`. ## Cut order this implies

The cluster has two clean lines and one tangled one. The two clean ones are `src/demote/` and `src/backfill/`: each folder is whole in the cluster (10 of 10 files), each ends in a command here (`skill demote`, `skill backfill`), and what each takes from outside is small (`src/schema/instinct.ts` and `src/check/references.ts` for the demotion; `src/utils/claude.ts` and one config key for the backfill). They are also the units that already look most like steps, a plan half and an apply half with a named refusal, so they are where the first registered steps in this part of the tree would be tried (gaps 2 to 4). The tangled one is the schema and the checker (`src/schema/`, `src/check/`), which three clusters share (gaps 6, 7 and 9), and which everything else in the cluster stands on.

Taken first, `src/schema/frontmatter.ts` (gap 8): it is a leaf with 11 outside importers, and nothing else moves until it can be imported from a package. Then `src/schema/` made whole (gap 6) and `src/check/` made whole (gap 7), with the helper that ties the lessons report to the demotion pass (gap 10) moved at the same time, because the checker, the schema and the inventory call one another across the three clusters and have to be made one package or none. Then the demotion pass and the backfill, each with its command (gaps 1 to 5, 11), and the two checks with `check-report.ts` last among the commands, since the inventory depends on the checker and not on the command. Taken last, the pipelines and their tests (gaps 12 to 14): `project-skills-check.test.ts` stays at the repository root as a repo-level check, and `backfill-pipeline.test.ts` and `demotion-pass.test.ts` move with the commands they drive.
