# Trace: `c05-sessions`

Coverage: 141 of 141 cluster members read, the 141 files `docs/survey/import-graph.json` lists for `c05-sessions`; all 141 are tracked by `git ls-files`, and no tracked member was left unread. The 61 non-test members (60 source, 1 test support) were read for their module notes and exports; the 80 test files were read through the graph and `docs/survey/test-index.json` only.

The largest cluster in the import graph with no trace file once `trace-c01-github.md`, `trace-c02-active.md`, `trace-c03-config.md` and `trace-c04-sqlite.md` exist: 141 files, 61 of them source or support and 80 tests, 395 edges inside it. The cluster is **what a person reads and does with a run that is already on disk, and the housekeeping around it**: the session records and events of a loop (`src/loop/`, five source files, with `src/start/loop-events.ts` and `src/start/worktree-dir.ts`), the `rafa loop` commands that act on them (`list`, `status`, `pause`, `resume`, `stop`, `wait`), `rafa cleanup` with the whole of `src/cleanup/` (eight source files), `rafa status` with the whole of `src/status/` (seven), the effort dashboard and trend readers (`src/effort/dashboard*.ts`, `report-trend*.ts`, `report-args.ts`, `trend-stats.ts`), the state table's wiring for `rafa next` (`src/next/readings.ts`, `sources.ts`, `owner-gate.ts`), the owner gate's readers (`src/board/codeowners.ts`, `board-owns.ts`, `owner-resolve.ts`, `board-body.ts`, `src/pr/owner-approval.ts`), `rafa self-update` over `src/runtime/install.ts`, `rafa plan list` and `plan show`, and three leaves several clusters stand on: `src/project/scope.ts`, `src/pr/types.ts` and `src/commands/plan/plan-files.ts`. Its hub is `src/loop/sessions.ts` (51 in-cluster edges, `src/commands/plan/plan-files.ts` second with 33, then `src/pr/pull-requests-double.ts` with 24); the highest betweenness belongs to `src/next/sources.ts` (26,155, rank 15 of the whole graph), then `src/cleanup/index.ts` (9,867, rank 40), `src/project/scope.ts` (9,791, rank 41), `src/status/sections.ts` (9,429, rank 43) and `src/loop/sessions.ts` (8,784, rank 48).

The contract the exports are read against is `run(ctx, options)` from #119 (step registry, guards with a class, consent in `ctx.answered`, `--dry-run`) and config and flows through define-config from #118 and #71. Neither has landed, as `trace-c03-config.md` and `trace-c04-sqlite.md` record: `src/steps/` and `src/flows/` do not exist, no source file imports `@open-tomato/define-config`, and `src/config-load.ts` still does its own merge. So every "present" below means present in today's shape, and every gap is what a cut has to change to reach the contract. Unlike `c04-sqlite`, this cluster is not a package in waiting: it has no entry file, no `package.json` subpath, and nothing outside the repository imports it. It is a cluster by use, not by design, and its largest piece, the loop's session record, is read by 15 non-test files of other clusters.

Nothing here is a registered step. These are the units the cluster contributes to a loop run or a command, with the guard that decides each and the class #119's vocabulary would give it. The classes are an assignment from `docs/workflow-checks.md` §2 and §5 and the source; no code declares them. "Behaviour" means no setting or flag turns the refusal off.

| Step (today's unit) | File | Guard that decides it | Class |
| --- | --- | --- | --- |

| append a loop event | `src/start/loop-events.ts` (`emitLoopEvent`, `bindEventsFile`) | best effort: a failed append warns once on stderr and never throws into the loop; no event opens the effort store | behaviour |
| stop, pause, resume | `src/commands/loop/stop.ts`, `pause.ts`, `resume.ts` over `loop-sessions.ts` | the pick is a session reading `running` or `paused`; `pause` and `resume` write only over the state they move from (`onlyFrom`), refuse a `stopped` or `done` run, and leave an already moved one alone with exit 0; `stop` sends SIGINT to the record's pid and marks nothing, the loop does | 🔒 |

The ⚠️ class has one home here, which `trace-c04-sqlite.md` records as having none in its cluster: `dangerous.selfUpdateDuringLoop` is read by `src/commands/self-update.ts` (and by no other file of the cluster), so a package that owns `self-update` has to declare it as the `passedBy` of a 🔒 guard. The 🧭 class has two: the notice (`status.notice`) and the checklist, which is a question asked of a person, and the contract has no place for it except `ctx.answered`.

Consent: the cluster has the first typed answers in the survey. `rafa cleanup` asks a grouped `multiSelect` (`src/cli/prompt/multi-select.ts`, `c06-command`) for the ticked rows, one question per Not-pushed row (`notPushedQuestion`) and a final yes or no, through `createLinePrompter` (`src/cli/prompt/confirm.ts`, `c01-github`). No other command of the cluster asks anything.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **A run's record from start to end:** `loop start` (outside) drafts a record → `SessionConflictError` on a live run on the branch → the record is written under `.rafa/runs/<id>.json` → `bindEventsFile` names `.rafa/runs/<id>.events.ndjson` → each task and wrap-up phase appended as one event → the state changes on `pause`, `resume`, `stop` and the run's end (`SessionChange`, with `onlyFrom` when a command must see the state it expects). `src/loop/sessions.ts`, `src/start/loop-events.ts`; the writer is in `c02-active`, so the flow crosses the boundary twice.
2. **`loop wait`:** the session picked as `loop status` picks it → every `WAIT_POLL_MS` the events file read from its last offset, the record and its pid, then the awake clock → the first reason asked for names the line and the exit code → `--timeout` ends it with 16. `src/commands/loop/wait.ts`, `loop/events-file.ts`, `wait-reasons.ts`, `awake-clock.ts`.
3. **`loop stop`, `pause`, `resume`:** the pick → a refusal on a `stopped` or `done` run → for `pause` and `resume` the record rewritten with `onlyFrom`; `stop` instead sends SIGINT to the pid, and the loop (`src/start.ts`, `c02-active`) marks the running task `[BLOCKED]`, stores its report and writes `stopped`; the command polls the record until it reads `stopped` or `done`. `src/commands/loop/stop.ts`, `pause.ts`, `resume.ts`.
4. **`rafa cleanup`:** the five readings (`readBranches`, `readWorktrees`, `readPastHead`, `readRunRecords`, the provider's merged pull requests) → the groups and their rows (`groups.ts`) with each blocker → a grouped checklist answered → a question per Not-pushed row → a final yes or no → `cleanupSteps` in the fixed order (worktrees, branches, run records) → the runner answers each outcome without throwing; `--dry-run` prints each step's command line. `readCleanup` in `src/cleanup/index.ts`, `runCleanup` in `src/commands/cleanup.ts`, `cleanupSteps` in `src/cleanup/steps.ts`.
5. **`rafa status`:** six readings composed from existing readers (branch and plan, loops, pull request, board, claims, housekeeping) → each section is its own `Section` and an unread one is named, not hidden → text or json, and in text mode a snapshot written for the notice. `readStatusSections` in `src/status/sections.ts` (737 lines), `renderStatus` in `render.ts`.
6. **The since-last-command notice:** `before` loads the config for `status.notice` → takes a reading and compares it with the snapshot → one stderr line or none; `after` writes the reading over the file. `createStatusHook` in `src/status/hook.ts`, `takeSeenSnapshot` in `seen.ts`.
7. **`rafa next`'s state table sources:** one `loadConfig` → git, the session records, the plans directory, the pull request provider, the board listing and the claims → `NextSources` handed to the table, which decides and prints nothing. `openNextSources` in `src/next/sources.ts`, `src/next/readings.ts`; the decision is `src/next/state.ts` (`c06-command`).
8. **The owner gate:** the changed paths of a pull request → `owningBoard` for each (CODEOWNERS' last match, else the deepest `Owns:` folder, else the whole-repository board) → each owner resolved with `gh api` (`createOwnerResolver`) → each approval and team membership read → the most severe of five answers. `readOwnerApproval` in `src/pr/owner-approval.ts` over `board/owner-resolve.ts`, `board-owns.ts`, `codeowners.ts`.
9. **Freeing a loop worktree for a merge:** the holder of the head branch → one level below `loop.worktreeDir` and named for the stub → no live loop and a clean tree → `CLOSEOUT-<stub>.md` and `PLAN_TRACKER-<stub>.md` copied to the main checkout → `git worktree remove`. `freeLoopHolderBeforeMerge` in `src/commands/pr/merge-loop-worktree.ts`, called from `src/commands/pr/merge-refuse.ts` (`c06-command`).
10. **`rafa self-update`:** the live-loop reading of the session records → `installRuntime` (`package.json` is rafa's, `plan.dir` has no open task, no runtime for the version) → `bun run build` → `dist/` copied → `~/.rafa/bin/rafa` linked. `createSelfUpdateCommand`, `liveLoopsOf` and `src/runtime/install.ts` (573 lines).
11. **The effort dashboard and trend:** the status widget over the loops (`dashboard-status.ts`: the by-task and by-progress estimates) → `buildReport`, `readSkillsReport` and the trend rows from the store (`c04-sqlite`) → `trend-stats.ts` (quantiles, outliers, direction) → `formatDashboard`. `readDashboard` in `src/effort/dashboard.ts`, `report-trend.ts` (550 lines).

## Cut order this implies

The cluster has three lines through it that a cut can use. The inner one is the loop's record: `src/loop/` with `start/loop-events.ts` and `start/worktree-dir.ts` has few imports out (the config's types, `scope.ts` and `src/utils/plan-stamp.ts`) and is the biggest source of cross-cluster edges (gap 9). The second is `src/cleanup/`, whole in the cluster, with `src/commands/cleanup.ts` and its render and doctor files: it imports git, the pull request provider and the config, and is the best candidate for the first registered steps (gap 4). The third is the board's owner gate (gap 13), which belongs to `c01-github` and moves out before it moves anywhere else.

Taken first, `scope.ts` and the project half of `plan-files.ts` move down to the package that holds `RafaContext` (gaps 7 and 8), because 88 of the 163 inbound edges end there and nothing else in the cluster can leave while the project's resolver is a plan file. `pr/types.ts` and the test doubles (gap 15) go with the pull request port. Then the loop's record and its six commands (gaps 9 and 10), then `cleanup` as the first step list (gap 4). Taken last, `status` with its six sections (gap 11) and the notice hook (gap 12), because they import every other cluster's reading, and `rafa next`'s sources (gap 13) and the effort readers (gap 14), which wait on the board's and the store's packages to exist.
