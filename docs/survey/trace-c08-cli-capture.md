### Commands

Both satisfy the superset shape `commandProblem` checks (`subject`, `action`, `summary`, `flags`, `examples`, `outputs`). Four things a package has to take on:

- The `RafaCommand` type, `RafaContext`, `CommandExit` and the output events are in `c06-command` (`src/cli/command.ts`, `dispatch.ts`, `registry.ts`); the 6 edges into `c06-command` from the product half are two files (`init.ts` and `update/current.ts` import `src/cli/command.ts`), and the harness imports `dispatch.ts` and `registry.ts` to build a dispatch for a case.
- `init` is the only command of the roster that creates the project the dispatcher otherwise refuses without (`needsProject: false`). A package that owns it needs nothing of the dispatcher's project resolution, and the package that owns the dispatcher has to leave one command out of it.
- `init` composes three steps from other clusters (the board, the epic guard, the relationships move, all `src/commands/init-board.ts`, `c01-github`) and the PATH and agent warnings. Its tests (`init.test.ts` at the index cap of 128, `init-scratch.test.ts`, `init-release.test.ts`, `src/tests/init-scope.test.ts`) are what pins the order the module note spells: the scopes, the `.gitignore`, the user scope, the release, the board, the epic guard, the relationships move.
- `update current` is the only `update` action not in `c06-command`; its siblings are stubs, and they are the contract's `update next` and `update latest` whenever they are written (`src/project/update-range.ts` names both in its refusal messages).

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **`rafa init`:** `expectNoArgument` and the flags read at the top (`--board`, `--epic-guard`, `--release`, `--yes`) → the root (`--root`, `--yes`, or the prompt listing `rootCandidates`) → refusals before a write (`scaffoldConflicts`, `loadConfig`, the `.gitignore` markers) → the project scope → the `.gitignore` block and its digest → the user scope → the release step → the board step → the epic guard step → the relationships move → the `PATH` and agent warnings → `renderInit` or the json result. `runInit` in `src/commands/init.ts` (line 599), `initialise` (line 474).
2. **`rafa update current`:** the lock read (`readProjectLock`) → the range (`readCurrentRange`) → the conflicts check → `readUpdatePlan` (folders missing, labels missing on a `gh` board, deprecations, lock change) → one line per step → `--dry-run` stops, else the warning and the question → `applyUpdatePlan` in order → the report; a failure is an `UpdateStepError` naming the step. `runUpdateCurrent` in `src/commands/update/current.ts` (line 273), `src/project/update-current.ts`.
3. **The standing notices:** `readDismissed(home)` → `pendingNotices` → on a terminal one question and an answer of three, without one the lines as warnings → `writeDismissed` on `d`. `offerNotices` in `src/notices/notices.ts`, wired by `src/notices/run.ts` (`c02-active`).
4. **The checkout guard:** the run's `CheckoutExpectation` (branch, head) → `readCheckout` (directory, toplevel, symbolic ref, HEAD) → `compareCheckout` → on a move the halt lines and the restore line → the halt (`[BLOCKED]`, no commit) is `src/start/checkout-watch.ts`'s. `guardCheckout` in `src/start/checkout-guard.ts`; the flow crosses the boundary twice and the six `checkout-guard*` tests under `src/start/` drive it at index 48.
5. **A spawned run in a scratch project:** `plantScratchRepo` (a git repository, a project config from `projectConfigText`, a HOME, a `bin/` with a stand-in `gh` from `plantStandInGh` and a stand-in `claude`) → `spawnedEnv` (PATH, `scratchHomeEnv`, `gitIdentityEnv`, `RAFA_TEST=1`) → `runRafa` or `startRafa` → `expectExit` and `expectEvent` on the captured run. `src/tests/cli-capture.ts`; the in-process alternative is `dispatchCaptured` over a registry the case builds. 91 of the cluster's tests and, with other clusters', 254 files stand on it.
6. **The project root choice and the main checkout:** `rootCandidates` (the git toplevel, the outermost monorepo marker above it, each carrying its refusal) → `promptForRoot` or `firstCandidate` or `namedRoot` → a real path (`ChosenRoot`); later commands re-find it with `scope.ts`, which falls back to `mainCheckoutOf` from a linked worktree. `src/project/roots.ts`, `root-choice.ts`, `worktree-root.ts`; the other half, `resolveScope`, is `c05-sessions`'.

## Cut order this implies

The cluster has two lines through it that a cut can use and one it should not. The first is `rafa init` with `src/project/`: `init.ts`, `init-release.ts`, `update/current.ts` and the eight project files form a nearly closed block (the two commands are imported by `src/commands/index.ts` and by nothing else outside the tests), and it is the best candidate for the first package after the config's: its steps are the ones the contract wants (one question each, a write only of what is missing, a `--dry-run` that `update current` already has), and it needs the config package to publish the template's defaults (gap 6) and the board and release packages to take their steps (gap 12). The second is the loop's start half: `start/checkout-guard.ts` and `notices/notices.ts` with the fifteen `src/start/` tests, which belong to `c02-active` and move with it (gaps 9 and 10). The line it should not follow is the cluster name: the harness is the largest part by file count (71 of 126 files) and is not a package of this repository's product.

Taken first, `worktree-root.ts` and the toplevel half of `roots.ts` move down to the package that holds `scope.ts` (gap 8), because the loop and the dispatcher both stand on them and nothing else in the product block can leave while the project root is read in two clusters; the project layer's upward imports (gap 7) are cut at the same time, since they are what would otherwise make the new leaf import a command. Then the test support goes to its own home (gap 13), before any other cluster is cut, because every cut's tests spawn through it. Then `init` and `update current` with their project files and `rafa.lock` (gaps 1 to 6 and 11), then the checkout guard and the notices with the loop (gaps 9 and 10). Taken last, the integration suites of the loop and the spawned `next-*`, `release-*` and `pr/merge-*` suites (gap 14), which wait on the packages that own the commands they spawn.
