# Trace: `c06-command`

Coverage: 128 of 128 cluster members read, the 128 files `docs/survey/import-graph.json` lists for `c06-command`; all 128 are tracked by `git ls-files`, and no tracked member was left unread. The 66 non-test members (64 source, 2 test support) were read for their module notes and exports; the 62 test files were read through the graph and `docs/survey/test-index.json` only.

The sixth cluster of the import graph by size (`c06`, after `c01-github` 265, `c02-active` 188, `c03-config` 180, `c04-sqlite` 163 and `c05-sessions` 141), and the first without a trace file once `trace-c01-github.md` to `trace-c05-sessions.md` exist: 128 files, 66 of them source or support and 62 tests, 383 edges inside it. The cluster is **the command surface itself and the commands that drive it**: the `RafaCommand` type, the context and `CommandExit` (`src/cli/command.ts`), the registry, the router, the dispatcher, the two rosters (`src/cli/help.ts`, `src/cli/describe.ts`), the module mounts, the copied `cli-core` (`src/cli/core/`), the raw-mode prompts (`src/cli/prompt/`), the `events`, `json` and stream output adapters, the static roster `src/commands/index.ts`, the process entry `src/rafa.ts`, and 22 registered commands (`rafa next` with all of `src/next/` it owns, five of the seven `rafa pr` actions, `plan create` and `plan validate`, `loop start`, `effort collect` and `effort report`, `describe`, `module exec`, `agent search`, `instinct flag`, and the seven `update` stubs). Its hub is `src/cli/command.ts` (79 in-cluster edges, `src/commands/index.ts` second with 36, then `src/cli/registry.ts` with 24); the highest betweenness belongs to `src/commands/index.ts` (193,950, rank 1 of the whole graph), then `src/commands/loop/start.ts` (21,781, rank 18), `src/commands/pr/merge.ts` (12,038, rank 34), `src/cli/command.ts` (10,506, rank 38), `src/commands/next.ts` (10,139, rank 39) and `src/next/hint.ts` (9,172, rank 45).

The contract the exports are read against is `run(ctx, options)` from #119 (step registry, guards with a class, consent in `ctx.answered`, `--dry-run`) and config and flows through define-config from #118 and #71. Neither has landed, as the earlier traces record, and all three issues (#71, #118, #119) are still open: `src/steps/` and `src/flows/` do not exist, no source file imports `@open-tomato/define-config` (the name appears only as a prerequisite line in the fixtures of `src/preflight/prerequisites-md.test.ts` and `src/start/preflight.test.ts` and in a doc comment of `src/preflight/prerequisites-md.ts`), and `src/config-load.ts` still does its own merge. So every "present" below means present in today's shape, and every gap is what a cut has to change to reach the contract. This cluster is the one the contract is written against: it holds the type #119 replaces (`RafaCommand.run`), the dispatcher that would call `run(ctx, options)`, and the two pieces of the repository that are nearest to a flow and a step list as data (`rafa next`'s state table and `ACTION_COMMANDS`, and the `rafa pr merge` refusals), which `docs/workflow-checks.md` §1, §3 and §7 draw. It is also the nearest cluster to a package that already ships: `package.json` exports `./cli` (`dist/cli.js`, built from `src/rafa.ts`) and `bin.rafa` points at it.

### Commands

All 22 satisfy the superset shape `commandProblem` checks (`subject`, `action`, `summary`, `flags`, `examples`, `outputs`, and `spends` through `spendsProblem`). The cluster is both a producer and the host of the type, so what a package has to take on is the type's own surface:

- The `RafaCommand` type is `Omit<CliCommand, 'run'>` plus `subject`, `action`, `summary`, `examples`, `aliases`, `lastingAliases`, `outputs` (`text`, `json`, `events`, `tui`), `deprecated`, `hidden`, `exec`, `needsProject` and `spends`; `CliCommand` is the copy in `src/cli/core/types.ts`, taken from open-tomato's `cli-core` at a named commit, so the contract starts from a copied package whose source `types.ts` says is not on the public registry.
- `commandProblem` is run twice: by `createCommandRegistry` for a core command (throws) and by `loadModuleCommands` for a module's entry (skipped with one warning naming the file). Both keep every spelling reachable and unambiguous: `help` is refused as a subject, an alias that collides is refused, a lasting alias the command does not also list is refused.
- `wrapPhaseZeroCommand` (`src/commands/wrap.ts`) is the one adapter in the repository from an old function to a `RafaCommand`: it hands a phase 0 function (`(args: string[], root: string) => Promise<void>`) the words after the routing words, drops the `--output` flag, appends the project root, and rejects before the call when the context holds no project. Four definitions use it (`loop start`, `plan create`, `effort collect`, `effort report`), each declaring the flags the engine's own parser reads, for the help and `describe`, which the engine never reads from the context.
- The `pr` actions share `src/commands/pr/pr-context.ts` (`openPrContext`: the config, the provider resolved and refused with exit 2 unless it is `gh`, the branch reader, the merge method, the base, the trusted authors, the relationships mode, the plan and worktree directories and the version guard's settings); `current`, `list`, `view`, `wait`, `merge`, and in `c07-index` `show` and `triage` all open it.
- `rafa next` runs other commands through `RafaContext.registry`: `src/next/actions.ts` finds the command by subject and action and awaits its `run`, so the registry reaches the command from inside another command and a `CommandExit` the command throws travels out untouched.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **One invocation:** `loadModuleCommands` imports and mounts each module's entry (a failure is a warning naming the file) → `routeLine` reads the words (version, help, command or one of five refusals) → the context is assembled against the command's `args` and `flags` with each deprecated flag read as the spelling it stands for → the start event (json mode) and the warnings → the project resolved unless `needsProject: false` (`no_project` otherwise) → `commandHook.before` (text mode, inside a project) → the deprecation lines → `run` with the output set as the active output and the command recorded as running → `commandHook.after` → the terminal `result` event and the exit code (`command_exit`, `command_error`, `result_unwritable`). `dispatch` in `src/cli/dispatch.ts`, `src/cli/route.ts`, `src/cli/modules.ts`, `src/cli/core/assembleContext.ts`; the process sets `process.exitCode` in `src/rafa.ts`.
2. **The two rosters:** the registry (`subjects`, `commands`, `mounts`, `actionsOf`) → `renderHelp` at three levels (root, subject, action) with the quick start derived from the first example of each subject, or `describeRegistry` as the schema 2 document with every field on every entry, `spends` and module of origin included. `src/cli/help.ts`, `src/cli/describe.ts`, `src/commands/describe.ts`; `src/tests/readme-spenders.test.ts` holds that the README's list of spenders is the roster's.
3. **`rafa next`:** one `pullBeforeRead` of the other devices' rows → the sources opened once, in the relationships mode the config names → `readNextState` (the first of 13 rows that matches, after the two pre-conditions) → the two lines → a stop (`dry-run`, `nothing-to-run`, `unchanged`, `capped`) or the ceiling → the question → `runAction` calling the registered command → the state read again, with the settle step read once after a merge and the `home` step after a loop action → the end-of-epic lines when the walk ran dry. `runNextChain` in `src/commands/next.ts` over `src/next/{state,actions,ceiling,lines,settle-step,epic-end,relations-mode,preconditions}.ts`; the sources are `c05-sessions`'.
4. **The closing hint:** the sources opened and the state read once, inside two seconds → a question where there is a terminal, the printed command where there is none → a yes runs the one action through `runAction` with the caller's output stripped of its `result` → no second reading. `endWithNextStep` in `src/next/ending.ts`, called as the last step of `pr merge`, `pr wait`, `pr triage`, `issue ready` and, through `endingWith`, `plan create` and `loop start`.
5. **`rafa pr merge`:** the pull request picked (the line's number, or the branch's) → its detail and its checks read, the plan CI row recorded → `refuseFromGit` (tree, untracked paths, the loop worktree step, the holder of the head branch, the verdict) → the release guard (`c09-version`) → the summary and the question (or the unchecked warning and its question) → `gh` merges → the one unchecked comment → the roadmap tick and the epic checklist tick → `cleanUpAfterMerge` as a list that never undoes the merge → the unblock reading → the follow-ups, `release settle` last → the ending hint. `runMerge` in `src/commands/pr/merge.ts` over `merge-refuse.ts`, `merge-unchecked.ts`, `merge-followups.ts`, `pr-context.ts`.
6. **`rafa pr wait`:** the pull request picked → the checks polled with the clock and a deadline in minutes → one line per poll → the verdict printed once with every check under it → exit by verdict. `runWait` in `src/commands/pr/wait.ts`.
7. **A phase 0 command behind the dispatcher:** the words after the routing words copied, `--output` dropped → the project root appended → the engine's own parser and run → whatever it throws goes on to the dispatcher. `wrapPhaseZeroCommand` in `src/commands/wrap.ts`; the engines are `src/start.ts` and `src/plan.ts` (`c02-active`), `src/effort/collect.ts` (`c03-config`) and `src/effort/report.ts` (`c04-sqlite`); `loop start` checks `--runtime` before the call.
8. **`rafa plan validate`:** the plan parsed → the agent roster resolved over the loaded tiers → agents and skills checked task by task → the effort-store rules → one line per finding, exit 1; the same check `loop start` halts on. `validatePlan` in `src/commands/plan/validate.ts`.
9. **A module action:** `allowList:` names a module whose `path` source loaded → its `commands` entry is mounted under `module/<name>` → `rafa module exec <module> <action>` routes through the mount → the action runs as a core one would, with its own `needsProject`. `src/cli/modules.ts`, `src/cli/registry.ts`, `src/cli/route.ts`, `src/commands/module/exec.ts`; `src/tests/module-seams.test.ts` drives the fixture end to end.
10. **A raw-mode prompt:** the terminal seam checked (refuse with no terminal) → `rawSession` switches raw mode on → keys decoded and the frame redrawn → an answer, `null` on Escape, or `CommandExit` 130 on Ctrl-C → raw mode off however it ended. `src/cli/prompt/*.ts`; `src/tests/prompt-restore.test.ts` spawns a child that is interrupted mid-prompt.

## Gaps

Every export that is missing or partial, with the file a cut would have to change. Gaps 1 to 3 are the contract itself and would be the same for any cluster; gaps 4 to 17 are specific to this one.

1. **No `run(ctx, options)` for the cluster's commands** (commands, partial). `run` takes `RafaContext` and returns `Promise<void>`. A cut changes `src/cli/command.ts` (the type), `src/cli/dispatch.ts` (what it does with a result and a refusal), `src/commands/wrap.ts` (the one adapter, which would become the shim from `PhaseZeroCommand` to the new `run`) and the 22 definitions under *Registered commands*; the 115 outside files that import `command.ts` change with it, which is why this is the first thing to move.
2. **No step registry or guard class** (steps, missing). Guards are code inside the units. A cut adds the registry (`src/steps/registry.ts`, not yet present) and moves each guard in the *Steps with guards* table into a step: `src/commands/pr/merge-refuse.ts` and `merge.ts` (the verdict, the tree, the worktree), `src/commands/pr/merge-unchecked.ts`, `src/next/preconditions.ts`, `src/next/ceiling.ts`, `src/board/leak.ts`, `src/cli/prompt/terminal.ts` and `src/cli/dispatch.ts` (the project). The `required` set a loader needs is every row marked 🔒; no file says today which of its refusals those are, and `docs/workflow-checks.md` §5 records that the state table is "the third copy of most 🔒 rows": `src/next/state.ts` and `preconditions.ts` re-read what `merge-refuse.ts` and `readMergeRefusal` refuse on.
3. **No consent in the context** (steps, missing). `src/next/ceiling.ts` takes the `--yes[=<ids>]` list and `src/commands/next.ts` asks through its own `NextAsk`, `src/commands/pr/merge.ts` and `merge-unchecked.ts` each open a prompter, and `src/next/ending.ts` opens a fourth; #119's `ctx.answered` has nothing to give them. A cut turns the ceiling's ids into pre-seeded `ctx.answered` keys, makes `ALWAYS_ASKED` the keys that cannot be pre-seeded, drops `QUESTION_HANDED_OVER` in `src/commands/next.ts` (the only action whose question is the command's own), and has `pr merge` and `endWithNextStep` read the answer from the context instead of building a prompter.

## Cut order this implies

The cluster has three lines through it that a cut can use. The inner one is the command foundation: `src/cli/` with `src/cli/core/`, `src/adapters/output/` and `src/rafa.ts`, which already has an entry and a published subpath (`./cli`), and whose only imports out are the five files gap 7 lists. The second is the `pr` surface: `src/commands/pr/` and `src/pr/{unchecked,workflow-triggers}.ts`, whose parts are in six clusters and whose guards are the nearest to the contract's steps (gap 11). The third is `rafa next`: `src/next/` with `src/commands/next.ts`, the only flow as data in the repository, whose readings are in three other clusters (gap 10).

Taken first, `scope.ts` and the config formatter move down (gap 7), because 115 of the 158 inbound edges end at `command.ts` and no other cluster can leave while the type imports a config file and a project file. `run(ctx, options)` and `ctx.answered` (gaps 1 and 3) are decided here, in `command.ts`, `dispatch.ts` and `wrap.ts`, before any definition moves, since the 22 definitions and the 65 outside ones all change with them. Then the roster becomes an aggregate (gap 4), the output adapters and the prompts come into the CLI package (gaps 8 and 9), and the four wrapped definitions go to their engines' packages (gap 6). Then the `pr` package, with `merge-refuse.ts`, `merge-unchecked.ts` and the follow-ups as the first registered steps (gap 11), because its guards are already a refusal order read before the first question. Taken last, `rafa next` (gap 10), because its rows read the board, the loop's records and the pull request port and wait on all three packages to exist, and the stray files and the misfiled tests (gaps 15 and 16), which move when their owners do.
