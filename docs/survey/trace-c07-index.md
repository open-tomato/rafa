### Commands

All six satisfy the superset shape `commandProblem` checks (`subject`, `action`, `summary`, `flags`, `examples`, `outputs`); `pr triage` is the only one with `spends`. Four things a package has to take on:

- The `RafaCommand` type, `RafaContext`, `CommandExit` and the output events are in `c06-command` (`src/cli/command.ts`); the 21 edges into `c06-command` from this cluster are five files, and `src/commands/pr/pr-context.ts` (`openPrContext`, `pickPullRequest`, `PrSeams`) is the one every `pr` action shares: it reads the line, the config and the provider in that order, so a stray word spawns no `gh`. `show.ts` and `triage.ts` both build on it and it is in `c06-command`, so the two commands cannot leave without it.
- The four claim commands share `src/commands/claim/release.ts`: `readIssueArgument`, `readClaimStoreId`, `readIssueBranches`, `findOwnedBranch`, `pushOnClaimTip`, `ClaimCommandSeams` and `ClaimSeamsFactory` are exported from it and imported by `hand.ts`, `accept.ts` and `take.ts`; all four also import `createStartPreflightClaim` from `src/start/preflight-claim.ts` for their seams, so the commands lean on a loop-start module.
- `rafa pr triage` is the largest command of the cluster by far: `triage.ts` (699 lines) assesses, `triage-read.ts` gathers (failing logs, workflow count, conflict files), `triage-report.ts` renders, `triage-trust.ts` applies the trust reading, `triage-resolve.ts` (712) runs the attempts, `triage-convert.ts` converts a `conflict-version` stamp in code, `resolve-loop.ts` spawns `rafa loop start --plan=<file>`, and `last-triage.ts` is `pr show`'s end of the same comment. It ends with the next-step hint through `src/next/ending.ts` (`c06-command`), whose `HINT_FLAG_SPEC` it declares as a flag.
- `rafa pr triage --resolve` spawns the loop as a subprocess, so the one command here that calls another is a command spawning the CLI; the contract has to let a step run `loop start`, or the pinned plans have to run through a flow.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **A claim from `plan create` to `loop start`:** `resolveAndClaim` runs the command's cheap refusals first (stub, plan already there, references check) → `claimPlanIssue` reads this device's store id (`claims/device.ts`) and fetches `feat/rafa-*` once → the remote's reading decides (push a new claim branch, take with a lease, or stand) → `rafa:claimed` put on the issue → the planning session. At `loop start`, `readRunClaim` re-reads, retries a claim left on the local branch, refuses a device that does not own it and swaps the label to `rafa:in-development` on a first dispatch. `src/claims/plan-claim.ts`, `src/commands/plan/claim-route.ts`, `src/start/preflight-claim.ts`; the callers (`src/plan.ts`, `src/start.ts`, `src/start/preflight.ts`) are in `c02-active`, so the flow crosses the boundary twice.
2. **Claim ahead:** `aheadEnabled` → `nextUndoneLine` off the walk's lines (one candidate, never more) → `resolveAheadTarget` (only on the home issue's board) → both issues' branches read off the same fetch → one `git push --atomic` of both refs, both or neither; a refusal over the home branch refuses the run, one over the line ahead leaves the home issue `unclaimed` (`ahead-taken`). `src/claims/ahead.ts`, `plan-claim.ts`, `claim-route.ts` (`aheadRequestOf`).
3. **A claim lost at the end of a run:** the wrap-up pushes `feat/<stub>` and is refused → `readRefusedPush` fetches and reads the owner, keeps this device's commits on `lost/<stub>` → `claimLostReport` → `verifyPullRequest` throws `CommandExit(1)` with no compare URL and no advice to push → the run is recorded `stopped`, not `done`. `src/claims/lost.ts`, `src/start/pr-lifecycle.ts`; the driver is `src/start/wrap-up-run.ts` (`c02-active`).
4. **A handover between two devices:** on device A, `claim hand --to` reads the store id, fetches, reads every branch of the issue, finds the one it owns and pushes a handover commit under a lease; on device B, `claim accept` finds the branch whose latest ownership commit is a handover to its store (`offerOf` names what ended an offer that is gone) and pushes an accept commit; `--withdraw` ends the offer before B accepts, and `release` and `take` are the same walk with their own guard. `src/commands/claim/hand.ts`, `accept.ts`, `release.ts`, `take.ts` over `src/claims/git.ts` and `record.ts`; `src/tests/claim-commands-spawned.test.ts` proves the five scenarios over real git from separate clones of one bare remote.
5. **The wrap-up's last gate:** `verifyPullRequest` reads the provider (`none` pushes and prints the compare URL, then stops) → `gh` unusable skips → finds the pull request → `waitForChecks` polls the rows → a red or conflicting result spends a repair session (a Claude session whose prompt names `origin/<base>` and the lockfile restore), up to `--ci-attempts` → escalation. When the wrap-up and its retries ended with no pull request, `openRunnerPullRequest` checks the tree, pushes and creates one. `src/start/pr-lifecycle.ts`, `src/start/runner-pr.ts`, `src/pr/checks.ts`, `src/pr/none.ts`.
6. **The branch offer:** `readBranchOffer` (stand aside or offer) → the question or `--create-branch` → `treeRefusal` → `branchSteps` for the route (`create`: fetch, read the standing, fast-forward, `switch -c`; `switch-local`; `switch-remote`: `switch --track`) → `readStepOutcome` after each step, whose refusal wording `src/next/sync.ts` follows. `src/start/branch-decision.ts`, `src/start/branch.ts`; `src/tests/branch-integration.test.ts` runs it over a real git and a bare remote.
7. **`rafa pr merge` over this cluster's data:** the command (`c06-command`) gathers tree, merge state, checks and worktrees → `readMergeRefusal` in the order tree, state, checks, worktrees → `gh` merges → `cleanUpSteps` is walked; a failure prints `remainingFrom` the same array and never undoes the merge. `src/pr/merge.ts` is the whole of the decision and the step list; the driver is `src/commands/pr/merge.ts` and its `merge-*` files.
8. **`rafa pr triage`:** the line, then the config and the provider (`openPrContext`) → a target (`selectTriagePullRequests`, `c05-sessions`) → per pull request `get`, `checks`, `comments` → the trusted marker comment (`readTrustedTriageComment`) → `readTriageRerun` before any log → failing logs, workflow count and conflict files (`triage-read.ts`) → `classifyTriage` → one comment written or edited (`writeTriageComment`) → `recordPlanCi` (`c04-sqlite`) → `renderTriage` → the next-step hint. `src/commands/pr/triage.ts` is the order; `src/pr/triage/` is the pure half.
9. **`rafa pr triage --resolve`:** `requireTrustedResolveAuthor` first → `crossRepositoryRefusal` → a `conflict-version` class converts in code (`triage-convert.ts`: worktree, conversion, push never forced, worktree removed, no attempt spent) or a pinned plan is chosen → worktree added → the counter raised into the comment → the plan filled (`pr/plans/load.ts`), given its `budget=` (`pr/plans/budget.ts`) and written outside the worktree under `<home>/.rafa/resolve/pr-<n>/attempt-<k>` → `rafa loop start --plan=<file>` spawned in the worktree → `waitForChecks` → a fresh assessment → `readAttemptRepeat` → next attempt or stop with exit 3 and the follow-up prompt. `src/commands/pr/triage-resolve.ts`, `resolve-loop.ts`, `src/pr/worktree.ts`, `src/pr/triage/attempts.ts`.
10. **`rafa pr show`:** the line → provider → `pickPullRequest` → `get` (a failure refuses) → `checks` and `comments` (each a degraded section on failure) → `readLastTriage` → the closing issues (`readClosingIssues` in the adapter, marked by `show.ts` where the provider links an issue the body names by no keyword and the reverse) → `renderShow` or the json fields `PR_SHOW_JSON_FIELDS`. `src/commands/pr/show.ts`, `last-triage.ts`, `src/pr/gh-closing-issues.ts`; `src/tests/pr-show-closes-integration.test.ts`.
11. **The claim readings behind `rafa status` and `rafa roadmap`:** `readClaimBranches` lists `refs/remotes/origin/feat/rafa-*` with one `for-each-ref` and no fetch → `readClaims` joins ownership, the stage label and the stale state (`readClaimState`); the roadmap's taken reading instead fetches once on the first line that asks (`createRemoteClaimReader`) and weighs each branch (`weighBranchClaim`). `src/status/claims.ts`, `src/board/roadmap-claims.ts`.
12. **The fast-forward of `rafa next`:** `fastForwardBase` over the same `GitRunner` as the merge clean-up and a base standing read with `parseBaseStanding`; a diverged base is refused with git's words quoted. `src/next/sync.ts`.

## Gaps

Every export that is missing or partial, with the file a cut would have to change. Gaps 1 to 3 are the contract itself and would be the same for any cluster; gaps 4 to 17 are specific to this one.

1. **No `run(ctx, options)` for the cluster's commands** (commands, partial). `run` takes `RafaContext` and returns `Promise<void>`. A cut changes `src/cli/command.ts` (the type) and the six files under *Registered commands* (`src/commands/pr/show.ts`, `triage.ts`, `src/commands/claim/{release,hand,accept,take}.ts`); for the `pr` subject the other five commands in `c06-command` (`src/commands/pr/{current,list,merge,view,wait}.ts`) and the `merge-*` parts in `c09-version` have to move together so that each subject is one package's, whereas the `claim` subject is already whole.
2. **No step registry or guard class** (steps, missing). Guards are code inside the units. A cut adds the registry (`src/steps/registry.ts`, not yet present) and moves each guard in the *Steps with guards* table into a step: `src/claims/plan-claim.ts`, `src/start/preflight-claim.ts`, `src/claims/lost.ts`, `src/commands/claim/*.ts`, `src/start/branch-decision.ts`, `src/start/pr-lifecycle.ts`, `src/start/runner-pr.ts`, `src/pr/merge.ts`, `src/board/trust.ts`, `src/pr/triage/attempts.ts`, `src/pr/worktree.ts`, `src/pr/provider.ts`, `src/pr/preflight-items.ts`, `src/next/sync.ts`. The `required` set a loader needs is every row marked 🔒; no file says today which of the refusals are those, and several are read twice, here and again in `src/next/state.ts` or `preconditions.ts` (`docs/workflow-checks.md` §5 lists tracked files modified, base diverged and checks red or absent among them).

## Cut order this implies

The cluster has three lines through it that a cut can use. The inner one is the port: `src/pr/` (the adapter, the check readers, the merge data, the provider and `none`, the worktree steps) with `src/pr/types.ts`, `git.ts` and the fakes from the clusters around it, whose only outside coupling is the config reading `MERGE_METHODS` (gap 9); it is imported by 50 non-test files and nothing in it imports a command. The second is the claim protocol: `src/claims/`, the four commands, `claim-route.ts`, `status/claims.ts`, `roadmap-claims.ts` and the two claim modules of `src/start/`, which needs only `GitRunner`, the board's seam and the branch names (gap 6), owns the one subject that is whole in the cluster and has the only end-to-end tests that spawn two real devices. The third is the triage (gap 12), which is a closed set over the port and `trust.ts`.

Taken first, the leaves that every line stands on: `src/schema/project-id.ts` and the move of `CheckRow` and `ChecksVerdict` (gaps 10 and 17), the ref constants out of `branch-decision.ts` (gap 6) and the fakes into test support (gap 11); none changes a behaviour and each takes a file out of most tests' reach. Then the port with its types as one package (gaps 5 and 9), with `cleanUpSteps` as the first registered steps, since it is already a step list (gap 4). Then the claim protocol, as the package that owns the `claim` subject whole (gaps 1, 6 and 7). Then the triage, after the port and after `trust.ts` has moved to the board (gaps 12, 13 and 15). Taken last, the six `src/start/` files and the three CI defaults (gaps 14 and 16), because they stay with the loop and take the port and the claims as seams, and `issue-board.ts` and `trust.ts` (gap 15), which wait on the board's package; the contract's three gaps (1 to 3) are met file by file as each piece moves.
