### Commands

The cluster owns no `RafaCommand`. What a package that kept the two would take on:

- **`rafa-hub` is not a rafa command and does not want to be one.** It is a server for a team, built into a container with `docker build -f packages/rafa-hub/Dockerfile` and started by `CMD ["bun", "/app/rafa-hub.js"]`, with its own version (`HUB_VERSION`, from `packages/rafa-hub/package.json`) and its own config file. Nothing in `src/commands/index.ts` runs it, and a `rafa hub` subject, if the contract wanted one, would be a new definition in `packages/rafa-hub/` registered through the manifest's `provides.commands` entry, a mechanism `src/modules/load.ts` already has and `rafa-sync-service` does not use.
- **The sync strategy is reached by commands that live elsewhere.** `rafa effort collect`, `effort report`, `next`, `status` and `loop start` call `src/effort/sync/contact.ts` (`c03-config`), which selects the strategy through the module registry; a command here would be `effort sync`, which does not exist. The strategy is the nearest thing in the repository to a command-free engine behind a port.
- **The three commands whose engine is `store/index.ts` are `effort collect`, `effort report` and `epic close`,** defined in `c06-command`, `c06-command` and `c10-index`; their definitions are not this cluster's and the entry only gives them the store. `trace-c04-sqlite.md` lists the same three from the store's side.

The one escape the cluster has is outside the config: `RAFA_TEST=1` with `RAFA_TEST_SECRETS_FILE` swaps the token reader for a file, in a process that sets both, and `packages/rafa-hub/src/store/testdata/broken-store.fixture.ts` plants faults by `RAFA_HUB_STORE_FAULT`, which only a fixture reads; neither is a pass of a guard. The 🧭 class has no member: `hub.auth.cacheFor` turns the token cache off with `false` or sets it from `1m` to `24h`, which is a trade the hub's operator makes and not a choice put to a person at a step.

Consent: no unit of this cluster asks a question. The strategy reads no typed answer, `effort.sync: service` and the allow list line are the project's own choice in `.rafa/config.yaml`, and `--dry-run` reaches the cluster only as the `dryRun` of the merge the pull makes.

### Config section

The cluster's own section is the hub's, and the server's four keys are the only settings declared by a package outside `src/`. The cluster reads three more keys of core's and one environment variable:

| Key | Default | Declared in | Read here by |
| --- | --- | --- | --- |

| `hub.port` | 7373, a whole number from 1 to 65535 (`DEFAULT_HUB_PORT`) | the same (`readPort`) | `bin.ts`, then `server.ts` |
| `hub.storePath` | `rafa-hub.sqlite` beside the config file (`DEFAULT_STORE_FILE`); a relative path resolves against the config file's directory | the same (`readStorePath`) | `bin.ts` (`dirname` and `basename`, handed to `openSqliteHubStore`) |
| `hub.auth.cacheFor` | `10m`, whole digits then `s`, `m` or `h`, from `1m` to `24h`; `false` is off (`DEFAULT_CACHE_FOR`) | the same (`readCacheFor`, `cacheForMs`) | `bin.ts`, then `identity/github.ts` |
| `RAFA_HUB_CONFIG` | unset; the path of the YAML file | not a key | `config.ts` (`readHubConfig`), `bin.ts` |
| `hub.url` | none (null) | `src/config-schema-hub.ts` (`hubUrl` with its reader, `HUB_SETTINGS`; `c03-config`) | `src/effort/sync/select.ts` through `hubContextOf`, then `sync.ts` as `ServiceHub.url` |

| `effort.sync` | `local`, one of `SYNC_STRATEGIES` | `src/config-schema.ts`, with the `SyncStrategy` type in `src/config-sections.ts` | `src/effort/sync/select.ts` (outside), which picks `service`; not read in the cluster |

So the slice is three keys of core's `hub` section and a second, separate section of four keys in a file of the hub's own, with the two halves of the section named the same (`hub.*`) and read from two files by two readers: the project's `.rafa/config.yaml`, where the server's keys are "unknown keys, warned about and acted on by nothing" (`src/config-schema-hub.ts`), and the hub's own `RAFA_HUB_CONFIG` file, where the client's keys are refused for the same reason. `src/config-schema-hub.ts` is the section file whose keys serve a package outside `src/`, in the shape the other four have (`HUB_DEFAULTS`, `HUB_SETTINGS`, `hubContextOf`). The `rafa-sync-service` strategy repeats one core default: `BUSY_TIMEOUT_MS = 5000` in `sync.ts` is `effort.busyTimeoutMs`'s default, written down again because the package may not import `src/config.ts`.

Tests: `packages/rafa-hub/src/config.test.ts` (index 1) holds the reader on its own; `src/config-schema-hub.test.ts` (`c03-config`) holds the client's keys.

### Flows

Multi-step paths the cluster drives end to end. Each is an ordered chain of functions with a refusal or a reading between steps and no flow declaration.

1. **Opening a selected store:** the config's `store` name → `CORE_ADAPTER_REGISTRY.find('store', name)` → `adapter.create({ repoRoot })` → a `SelectedEffortStore` whose `path(kind)` names the file; nothing is read or created until a call needs it. `selectEffortStore` in `src/effort/store/index.ts`.
2. **Collecting the session logs of a project and its worktrees:** `loop.worktreeDir` resolved against the root → the main folder and every folder whose name starts with the encoded worktree directory and a `-` → each folder's loose `*.jsonl` listed oldest first, ties by id → a session id kept from the first folder that holds it, the copies named as duplicates → the candidates handed to the collector. `projectLogDirs`, `listProjectSessionLogs`, `listSessionLogs` in `src/effort/session-log-dirs.ts`, driven end to end by `src/tests/effort-collect-worktrees-integration.test.ts` over a fixture HOME (three folders, one log held twice, another project's folder left out).
3. **Starting the hub:** `RAFA_HUB_CONFIG` read → the config parsed or refused with every problem → the server started on the port with the GitHub identity and a store opener → the store opened at start and again on the next request needing it once an attempt has failed → `/health` answers 503 until it has. `runHub` in `packages/rafa-hub/src/bin.ts`, `readHubConfig` in `config.ts`, `startHubServer` in `server.ts`; `SIGINT` and `SIGTERM` stop the server then close the store and exit 0.
4. **A request through the hub:** path and method (404, 405) → the identity port asks GitHub with the caller's token for `GET /user` and `GET /repos/{owner}/{name}` (401, 403, 503) → the route's action checked against what the caller may take → the store acquired (503) → the query checked → the body decoded by core's `decodeWirePayload` → the store's push, pull or status → the success or failure envelope → one `request` log line. `startHubServer`, `serveRoute` in `server.ts`; `openGitHubIdentity` in `identity/github.ts`.
5. **A push taken by the hub:** the payload's migrations checked against this build's catalogue (`HubUpgradeRequired`) → a payload with rows materialised as a scratch store → merged into the hub's store by `mergeStore` (the only route a row reaches it) → the merge's backup removed → the device's last push stamped. `openSqliteHubStore` in `packages/rafa-hub/src/store/sqlite.ts`; a pull is the store's `exportWirePayload` past the cursor with the caller's own origin left out.
6. **A device's contact with the hub:** `effort.sync: service` and a module line chosen in the config → `loadModules` registers `sync/service` → `selectSync` hands it `repoRoot`, `store` and the `hub` context → on `push`, the store's origin read from `store_meta`, the rows past the push cursor exported, sent under the origin, the cursor written once the hub took them → on `pull`, the hub asked past the pull cursor, the payload checked for migrations this rafa lacks, built into a scratch store and merged by `mergeStore`, the backup removed, the cursor written unless it is a dry run. `createServiceSync` in `packages/rafa-sync-service/src/sync.ts` over `client.ts`, `state.ts` and `token.ts`, driven by `src/effort/sync/contact.ts` (outside).
7. **Two devices converge through one hub:** each device spawned as `bun` over its own scratch git repository, each writing a commit row of its own and running `effort collect` twice, interleaved → every merged table read straight off each SQLite file and the hub's → equal content, then a third round that changes nothing. `packages/rafa-hub/src/two-devices.integration.test.ts` over `compare-merged-stores.ts`; `hub-unreachable.integration.test.ts` runs the same with the hub down, to hold that a device then uses its local store, prints one line and exits as it would have.
8. **A new adapter proving itself:** a factory handed to `hubStoreContract(name, factory)` or `identityContract(name, factory)`, each running the cases the port lists; a fixture that breaks one rule is run in a child `bun test` by `contract.test.ts` to hold that the suite fails it. `packages/rafa-hub/src/store/contract.ts` and `identity/contract.ts`, with `testdata/memory-store.ts` and `memory-identity.ts` as the second adapter of each port.

## Gaps

Every export that is missing or partial, with the file a cut would have to change. Gaps 1 to 3 are the contract itself and would be the same for any cluster; gaps 4 to 14 are specific to this one.

1. **No `run(ctx, options)` and no command at all** (commands, missing). The cluster registers nothing. A cut that wants `rafa hub` or `rafa effort sync` as commands writes the definitions in `packages/rafa-hub/` and `packages/rafa-sync-service/` and registers them either in `src/commands/index.ts` (the static list) or through the manifest's `provides.commands` entry that `src/modules/load.ts` already reads; `src/cli/command.ts` (the type) changes for #119's shape. `bin.ts` stays a separate executable unless a command wraps `runHub`.
2. **No step registry or guard class** (steps, partial). Guards are code inside the units. A cut adds the registry (`src/steps/registry.ts`, not yet present) and moves each guard in the *Steps with guards* table into a step: `src/effort/store/index.ts`, `src/effort/session-log-dirs.ts`, `packages/rafa-sync-service/src/sync.ts` and `client.ts`, `packages/rafa-hub/src/server.ts`, `identity/github.ts` and `store/sqlite.ts`. The `required` set a loader needs is every row marked 🔒; no file says today which of its refusals those are. The `service` strategy is the one place where the repository already swaps behaviour by a name a project chose: the module loader registers it as `sync/service` and `selectSync` picks it, which is #71's "swappable steps" in a form the registry in `src/steps/` would have to absorb or leave alone (`src/effort/sync/select.ts`, `src/modules/load.ts`, `src/adapters/registry.ts`).
3. **No consent in the context** (steps, missing). Nothing here asks, so a cut owes it nothing; `dryRun` stays a flag on the pull (`SyncPullRequest`) and reaches the contract as `ctx.dryRun` only if the strategy becomes a step.
4. **The hub's config is a section with no home in the schema** (config, partial). `packages/rafa-hub/src/config.ts` reads four keys by hand from a file of its own, and `src/config-schema-hub.ts` declares three more in core under the same `hub.*` prefix, each side refusing the other's keys as unknown. A cut either gives each package its own section under define-config (#118) and drops the shared prefix, or has the client's three (`hub.url`, `hub.tokenSecret`, `hub.timeout`) move to `rafa-sync-service` and be declared by the module, which the manifest cannot do today: `MANIFEST_KEYS` in `src/modules/manifest.ts` are `manifestVersion`, `types`, `provides`, `requires`, `prerequisites` and `source`, with no key for settings. `src/config-schema.ts` stops spreading `HUB_DEFAULTS` and `HUB_SETTINGS` and `RafaConfig` stops extending `HubSettings`.
5. **The client's section is in core and the package that reads it is not** (config, cut boundary). `hubContextOf` builds the `AdapterContext.hub` that `selectSync` hands the strategy, so a package outside the repository could not read its own section without core. A cut moves `src/config-schema-hub.ts` with the strategy, or has the module register its keys.
6. **The entry imports the registry, the registry imports the backends** (cut boundary). `src/effort/store/index.ts` imports `CORE_ADAPTER_REGISTRY` (`c03-config`), which statically imports `sqlite.ts`, `ndjson.ts` and `src/effort/sync/file.ts` (`c04-sqlite`): the cycle is `trace-c04-sqlite.md` gap 7. For this cluster it means a hub or a sync service that wants only the wire codec and `mergeStore` still imports `src/adapters/registry.ts` and the config module, and the hub's container, which copies `src` whole, bundles whatever of core they reach. A cut has `./store` export the selector over a registry it is handed, and the two packages import the entry without the registry; `src/effort/store/index.ts` and `src/adapters/registry.ts` change.
7. **The entry re-exports a type and two values from the config and the board** (cut boundary). `StoreBackend` and `STORE_BACKENDS` come from `src/config.ts` and `TRUSTED_PERMISSIONS` and `TrustedPermission` from `src/board/trust.ts` (`c07-index`), so the store's public surface depends on two other clusters for three names. A cut moves `STORE_BACKENDS` with the store (`trace-c04-sqlite.md` gap 4) and either moves `TRUSTED_PERMISSIONS` to a leaf the identity adapter imports, or takes the permissions list as `GitHubIdentityOptions` so that `packages/rafa-hub/src/identity/github.ts` imports nothing from core; `src/effort/store/index.ts`, `src/board/trust.ts` and `identity/github.ts` change.
8. **The packages copy what they may not import** (cut boundary). `packages/rafa-hub/src/testdata/scratch-home-env.ts` repeats `src/tests/scratch-home-env.ts` and the git identity of `src/tests/git-identity.ts`; `test-secrets.ts` repeats `SECRET_SERVICE` and `TEST_SECRETS_FILE_VARIABLE` of `rafa-sync-service`'s `token.ts`; `sync.ts` repeats `effort.busyTimeoutMs`'s default (`BUSY_TIMEOUT_MS`) and the text of `rafa effort move --to=sqlite` and `rafa self-update`; `src/tests/effort-collect-worktrees-integration.test.ts` spells the worktree directory default. A cut gives test support its own package, or accepts the copies as the price of the import rule.
9. **`session-log-dirs.ts` has no package of its own** (cut boundary). `src/effort/session-log-dirs.ts` (247 lines, imports `session-log.ts` only) is the collector's, has one non-test importer (`src/effort/collect.ts`, `c03-config`) and sits in this cluster because the graph found no better one: it does not read the store, a loop record or the config, and it takes the worktree directory as an argument. A cut moves it, `session-log.ts` (`c04-sqlite`) and `src/effort/collect.ts` together into the package that owns `effort collect`, and moves its test and `src/tests/effort-collect-worktrees-integration.test.ts` with them; it does not belong with the hub.
10. **The strategy loads by path, not by name** (cut boundary). `src/tests/sync-service-package-integration.test.ts` and the two integration tests name the package by a `modules:` `path:` line and an `allowList:` entry; nothing imports it, and `package.json` of the root does not list either package as a dependency (`workspaces` only). `src/modules/load.ts` reads only `path` sources in phase 1 and refuses `npm` and `github` ones ("installing a package is phase 7's"), so a project can use the package only from a checkout. Both packages are `"private": true` at version `0.0.0`, and the hub's only delivery is the Dockerfile; a cut that publishes `rafa-sync-service` has to wait on that install path.
11. **The hub bundles core** (cut boundary). `packages/rafa-hub/Dockerfile` copies `src` and `package.json` of the root and builds from `bin.ts`, so the container carries whatever `src/effort/store/index.ts` reaches; `packages/rafa-hub/src/bin.ts` also imports `../package.json` for `HUB_VERSION`. A cut leaves the Dockerfile on the repository root's context until the entry (gap 6) imports no registry; only then can the build copy the package and the entry rather than `src`.
12. **The two contract suites are source files that run tests** (cut boundary). `packages/rafa-hub/src/identity/contract.ts` and `store/contract.ts` import `bun:test` and are exported for an adapter written outside the package to run; they are graphed as source and counted among the 15, so the survey's source counts include two test suites. A cut names them test support (the `testdata` folder, or a suffix) and keeps them exported from the hub package for adapters written outside it.
13. **Two core files, one cluster, no common cause** (cut boundary). `src/effort/store/index.ts` is the entry of one package and `src/effort/session-log-dirs.ts` the helper of another, and they are reached by 398 and 358 of the 908 tests; nothing but the graph puts them together. A cut treats them as two decisions: the entry stays with the store (`c04-sqlite`) as its public surface, which is where `trace-c04-sqlite.md` gap 6 puts it, and the log reader goes with the collector (gap 9).
14. **The tests reach all of core through the entry** (cut boundary; test index). Of the 21 member tests, 5 are at 64 and 7 spawn a process; every package test that imports `@open-tomato/rafa/store` reaches 31 or 32 folders because the entry imports the registry (gap 6). A cut keeps the epic's fourth criterion only if those tests import the wire codec and `mergeStore` as one narrow folder and not through the registry; the cheap tests are already the ones that import nothing from core (`hub/config.test.ts`, `sync-service/token.test.ts`, the two testdata tests).

## Cut order this implies

The cluster has two lines through it. The inner one is the hub: `packages/rafa-hub/` (31 files, whole in the cluster) needs only the entry, and is a leaf nobody imports and already tested as a package, so it moves first and moves as it is, with the Dockerfile. The second is the sync service: `packages/rafa-sync-service/` (10 files) also needs only the entry and `./ports`, and it is the only member loaded by a manifest, which makes it the first candidate for a step or a swappable adapter in the sense of #71 (gap 2).

Taken first, the entry's three foreign names (gaps 6 and 7): `STORE_BACKENDS` and `StoreBackend` move into the store with `trace-c04-sqlite.md`'s gap 4, `TRUSTED_PERMISSIONS` becomes an option of the identity adapter, and the registry import goes out of `src/effort/store/index.ts`, because that one import brings the config module and every backend into each package and into every test of the two. Then the two packages' sections (gaps 4 and 5), once define-config exists, since each is a section of a package that is not core. `session-log-dirs.ts` and its two tests (gap 9) go with `effort collect` and wait on `c03-config`'s package. Taken last, any command for either package (gap 1) and the step registry's view of the strategy (gap 2), because they need the contract that has not landed.
