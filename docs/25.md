## What you get

When a task works something out, it becomes a lesson that later tasks can use. When two tasks disagree, a written rule settles it, instead of whichever wrote last. The rule lives in a pure library that imports nothing else from rafa and is tested on its own, so #27 can serve the same function over HTTP. The wrap-up stops asking a model to decide what to keep from `progress.txt`. Code picks the lessons that recurred, and the session only writes those into the page that owns their subject.

## Starting position

- **The record exists.**
  - File form: `src/schema/instinct.ts`, YAML frontmatter plus `## Action` and `## Cause`.
  - Confidence runs from 0.3 to 0.9. `action_hash` is computed when the file is read and never stored.
  - The port: `Learning` in `src/ports/index.ts`, with `push`, `pullBlessed` and `flag`. `MergeRule` is `new-trigger | same-action | higher-confidence | flagged`, and the gap is 0.10.
- **The adapter is phase 1's stub.** `src/adapters/learning/local.ts` appends to `.rafa/instincts/instincts.ndjson`, answers every push `new-trigger`, and blesses everything active. No command resolves it.
- **Only the demotion pass writes instincts** (`src/demote/*`, source `demoted`, as `.md` files). Nothing turns a task report's findings into instincts.
- **Findings stop at `progress.txt`.** Rows of the `findings` table (`src/effort/store/findings.ts`) are rendered into `progress.txt` before every dispatch (`src/utils/progress.ts`), and into the planner's `{PROGRESS_SECTION}`.
- **The wrap-up's promotion is unchecked.** `buildWrapUpPrompt` (`src/start/wrap-up.ts`) asks the session to read `progress.txt`, promote findings under a three-condition rule, and invoke a learn skill if one is present. Code checks none of that.
- **`.rafa/` is gitignored in this repository.** Lessons at project scope do not travel with a clone; only prose promoted into a tracked page does.
- **One key.** `learning.adapter` (default `local`) is the only learning setting.

## Design

### The library: `src/learning/`, exported as `@open-tomato/rafa/learning`

- **Decided: it lives in this repository, as its own subpath.** A lint boundary rule forbids it any import from the rest of `src/`. It becomes `@open-tomato/distributed-learning` by a move when #27 names its second consumer, which is #27's own condition. Why not a separate repository now: it would block this issue on a publish, the way `define-config` 0.1.1 blocks #118.
- **Pure.** No filesystem, no clock (`now` is passed in), no randomness. It takes and returns the port's `InstinctRecord`s, and it owns those types; the port re-exports them, so each type is declared once.
- **`actionHash(action)`** is `sha256(trim(lower(action)))`. It moves here, and `schema/instinct.ts` re-exports it.
- **A trigger's identity** is its text, trimmed, lower-cased, with whitespace collapsed. Two wordings of one trigger are two triggers. Fuzzy matching is rejected because its answer is not stable.
- **`merge(held, payload, now) → MergeResult`** settles each trigger over its whole set of actions, not pair by pair, so the result does not depend on push order:
  1. **`same-action`.** Records with one `action_hash` become one record:
     - `usage_count` counts distinct sources, so a session pushing twice is idempotent;
     - confidence is the usage-weighted mean, plus `0.05` for each distinct source beyond the first, capped at 0.9.
  2. **`higher-confidence`.** Among a trigger's distinct actions, the highest confidence leads. Every action more than `GAP` (0.10) below the leader is `discarded`: it stays in the push log and is never deleted.
  3. **`flagged`.** Every action within `GAP` of the leader is flagged together with the leader, and so is an exact tie.
  4. **`new-trigger`.** A trigger nothing held before is kept as it is.
- **The confidence arithmetic is the contract.** `GAP` and the per-source step are library constants, not settings, so two machines always reach the same verdict. #27's "same verdict the local adapter gives" depends on it.
- **`bless(held, { minConfidence }) → BlessedBundle`.** The active records that are not flagged and have `confidence ≥ minConfidence`. Ordered by confidence, then usage, then `id`.
- **`promotable(held, { after, minConfidence })`.** The blessed records with `usage_count ≥ after` that also meet `minConfidence`. This is "promotion on recurrence".

### Findings become lessons

- **The conversion.** A report finding that has a `resolution` becomes an instinct with source `task-report`:
  - `trigger`, `cause`, `kind`, `signal` and `artifact` are copied as they are;
  - `action` ← `resolution`;
  - `domain` comes from a new optional finding field in `PROMPT.md`'s report, and defaults to `workflow`;
  - `confidence` is 0.5, or 0.4 when the task ended blocked;
  - `evidence` is `{ plan, task, session, outcome }`;
  - `scope` is `project`.

  A finding with no `resolution` stays a finding only.
- **When it is pushed.** Once a task's report is recorded, the loop pushes that session's lessons to the adapter, with `source_id` set to the session id.

### The local adapter

- **It runs the library.** `merge` runs on every push and `bless` on every pull.
- **Held set and logs.**
  - The held set is the `.md` files `<root>/.rafa/instincts/<id>.md`. That is the reviewable form, and it is what `rafa instinct check|list|show` already read.
  - `instincts.ndjson` becomes the push log, one line for each decision.
  - `flags.ndjson` is unchanged.
  - Demoted records join the held set as they are.
- **The user scope is read-only here.** A pull gives the project's blessed records, then the user scope's (`~/.rafa/instincts`) for triggers the project does not hold. That is #26's order.
- **Registered commands.** `rafa instinct flag <id> <reason>` and `rafa instinct promote` are already in the command tree, unregistered; both are registered. `instinct list` gains `--blessed` and `--conflicts`; `--conflicts` shows the flagged groups side by side.

### The wrap-up

- **What is removed.** The promotion bullets: read `progress.txt`, the three-condition rule, invoke a learn skill.
- **What replaces them.**
  1. Code computes `promotable`.
  2. The prompt gets a `## Lessons to promote` list: id, trigger, action, artifact.
  3. For each lesson, the session either writes it into the page that owns the subject, or says why not, in a `rafa:promoted` block: `id → path` or `id → skipped: <reason>`.
- **Code checks the answer.** Every listed id must be answered, and every named path must have changed in the working tree. A promoted lesson gets `promoted_to: <path>`, a new optional field, and leaves injection, because the page now carries it. A missing answer is reported in the PR body. It does not block the PR.
- **With nothing promotable, the section is absent.**
- **`progress.txt` is unchanged here.** It is still rendered for task sessions and the planner. #23 adds lesson injection beside it.

### Config, shaped for #118

| Key | Default | Meaning |
| --- | --- | --- |
| `learning.adapter` | `local` | unchanged |
| `learning.bless.minConfidence` | `0.5` | the lowest confidence a lesson can have and still be blessed |
| `learning.promote.after` | `3` | how many distinct sources must confirm a lesson before it can be promoted |
| `learning.promote.minConfidence` | `0.7` | the lowest confidence a lesson can have and still be promoted |

- All four are local policy, allowed at every layer.
- In `rafa.config.ts` they are one `learning` map, which #118's merge treats by key.

## What can go wrong

- **A wrong lesson gets blessed.** `rafa instinct flag` removes it. A flagged record is never blessed, and a flag survives every later merge because it names the `id`.
- **Two wordings of one trigger never meet.** Accepted and documented. #57's assess can pair them.
- **One task inflates its own lesson.** `usage_count` counts distinct sources, and a session repeating a push is idempotent.
- **The wrap-up session ignores the list.** The `rafa:promoted` check reports each unanswered id in the PR body. The lessons stay in the store and are still injected by #23.
- **A hand-edited lesson file is invalid.** `rafa instinct check` names it, and the adapter skips it with a warning, as today.
- **The library and the port drift apart.** The library owns the types and the port re-exports them, so there is one declaration.
- **A later change makes merge depend on push order.** A permutation property test runs over the fixtures in every order.

## Definition of done

- Two sessions push the same trigger with different actions:
  - At 0.5 and 0.8, `rafa instinct list --blessed` shows the 0.8 action, and the push log records the 0.5 one as `discarded`.
  - At 0.5 and 0.55, both are flagged and neither is blessed. `--conflicts` shows them side by side.
- Two sessions push the same action: one record remains, with `usage_count: 2` and confidence 0.55.
- Three fixture payloads pushed in all six orders leave the same held set.
- `bun test src/learning` passes, and the boundary rule shows no import from outside `src/learning`.
- A fixture plan run with the stand-in `claude`, whose task reports a finding with a `resolution`, leaves `.rafa/instincts/<id>.md`, and `rafa instinct check` passes it.
- A lesson that reaches `learning.promote.after` appears in the wrap-up prompt's list. A `rafa:promoted` block that leaves it out is reported in the PR body.
