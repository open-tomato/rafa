Blocked by: #26 #25

## What you get

Skills are chosen when the plan is written and handed to the task that needs them, instead of hoping a session finds them. The planner sees a compact index of the skills a run can reach, and names them per task with `skills=`. At dispatch the loop resolves those names and gives the session a fixed `## Skills for this task` section. It also adds `## Lessons from earlier tasks`, holding the blessed lessons (#25) whose trigger matches the task. A control arm picks skills by tag, with no planner involved, and writes the same sections, so the two can be compared. The comparison follows a protocol written down before the first measured run, including what a null result means.

## Starting position

- **`skills=` goes nowhere.** It is parsed (`parseSkillList`, `src/utils/declaration.ts`) and stripped with the rest of the block. It maps to no flag and is not stored: `dispatches` has no column for it (`src/effort/store/dispatches.ts`). `plan needs` and `plan risk` read it; dispatch ignores it.
- **The planner gets no index.** Its slots are `PLAN_FILE`, `PREREQUISITES_FILE`, `PROGRESS_SECTION`, `PLAN_FORMAT` and `SPEC_CONTENT` (`src/plan.ts`). The only mention of skills is `dev-planner`'s "link to relevant `.claude/skills/` files".
- **The task prompt has no skill or lesson section.** `buildTaskPrompt` (`src/start/dispatch.ts`) puts together:
  1. the scoped-task line, which is the classifier key;
  2. the focus line;
  3. an optional blocker line;
  4. `PROMPT.md`;
  5. the injected plan;
  6. the known-missing notice.
- **Nothing counts skill use.**
  - `skills_used` in a report is parsed but not stored.
  - `src/effort/session-log.ts` reads counters only ("No prompt, no tool output"), so the name of a `Skill` tool call is never read.
- **A model-free ranker already exists.** `src/inventory/search/rank.ts` ranks inventory rows against words. The control arm's matcher reuses it.
- **From the blockers:**
  - #26 gives `resolveTiers`, meaning the winners a session is served, with rafa-tier items delivered to it, and the `{ROUTING}` slot.
  - #25 gives `bless` and the blessed bundle.

## Design

### The index (planner arm)

- **What it lists.** `renderSkillIndex(resolution)` writes one line per skill a loop session will see (#26's winners, minus items switched off): `name — tags — prevents` (or the `description` when there is no `prevents`).
- **How big it gets.**
  - Each line is cut at 160 characters, and the whole index at 8,000.
  - Past the cap, lines are kept in tier order, then by name, and the index ends with `N more: rafa skill list`.
  - Agents are not listed; `{ROUTING}` covers them.
- **Where it goes.** A new `{SKILL_INDEX}` slot in `plan-prompt.md`, after `{ROUTING}`.
- **What the planner is told.** `dev-planner` says to name the skills a task needs with `skills=`, only from the index, and that naming none is a valid answer.
- **Unknown names are refused.** `plan validate` and `loop start` preflight refuse a `skills=` naming anything `resolveTiers` does not resolve, naming the task line, exactly as they refuse an agent.

### Resolvers

- **Pure and exported:** `type SkillResolver = (task: TaskInput, resolution: Resolution) → ResolvedSkill[]`.
  - **`planner`:** the task's `skills=`, resolved by name.
  - **`tag`:** the control arm. It ignores `skills=`, ranks the resolution's rows against the task text and its stage context with `rank.ts`, and keeps the top 3 above the ranker's floor.
  - **`none`:** nothing; the "before" condition.
- **Lessons are chosen the same way under every arm, so the arms differ only in skills.** `selectLessons(task, bundle)` takes the blessed bundle (#25) and keeps a lesson when either:
  - its `artifact` path is named in the task text or its stage context; or
  - `rank.ts` scores its trigger against the task text above the floor.

  It keeps at most 5, highest confidence first.

### Prompt sections: one format whichever resolver made them

```
## Skills for this task
Invoke each with the Skill tool before you change anything it covers.
- `git-workflow`: Use when pushing a branch, opening or updating a PR, …

## Lessons from earlier tasks
- When <trigger>: <action> (confidence 0.70, from 3 tasks, lesson <id>)
```

- **Placement.** Both sections go after the blocker line and before `PROMPT.md`. The scoped-task line stays first, so `src/effort/classify.ts` is unaffected.
- **Empty sections are absent.** A task with nothing to hand out gets the same prompt it gets today.
- **The resolver's name never appears in the prompt.** It is recorded on the dispatch only, so a session cannot tell which arm it is in.

### Records

- **`dispatches` gains three columns:** `resolver`, `skills_offered` (JSON) and `lessons_offered` (ids). That is one migration.
- **A collector counts skill use.** `src/effort/skill-use.ts` reads each `Skill` tool call in a session log, in the main thread and in sidechains. It keeps only the tool's name and its `skill` input, and stores them in a new SQLite-only table: `skill_invocations(session_id, name, sidechain, count)`.
  - This is the one named exception to `session-log.ts`'s "no tool input" rule. Its module note says so.
  - Served rafa skills are matched under #26's name mapping.
- **Backfill.** `rafa effort collect --skills` runs the collector over sessions already recorded, which gives the "before".

### The measurement protocol, written before the first measured run

`docs/skills-measurement.md` is committed by this plan, and nothing in it changes after the first measured plan starts. It fixes:

- **Unit:** one task session.
- **M1, skill references per plan:** the distinct (task, skill) pairs invoked, divided by the plan's tasks.
- **M2, uptake:** the offered skills that were invoked, divided by the skills offered, per arm.
- **Before:** the last 3 merged plans of this repository, backfilled, arm `none`.
- **After:** at least 3 plans per arm (`planner` and `tag`). The plans are comparable when each comes from a `type:spec` issue of this repository and has 8 to 30 tasks. Arms alternate plan by plan, in roadmap order, set with `loop start --skills-resolver=`.
- **The reading, decided in advance:**
  - If `planner`'s M2 is not at least 10 points above `tag`'s over at least 30 tasks per arm, the index is not paying for its tokens. The default becomes `tag` and `{SKILL_INDEX}` leaves the planner prompt.
  - If neither arm's M1 beats `none` by at least 10 points, handing out skills does not change what sessions invoke. #24's `ignored` list is then read before anything more is built on skill delivery.
  - Either result is a finding, recorded in the doc with its date.
- **What it does not measure:** outcomes and causes. That is #24's report, which prints the per-arm table this protocol reads.

### Config, shaped for #118

| Key | Values | Default |
| --- | --- | --- |
| `task.skills` | `planner`, `tag` or `none` | `planner` |
| `task.lessons` | `on` or `off` | `on` |

- `loop start --skills-resolver=` overrides `task.skills` for one run.
- In `rafa.config.ts` they form a `task` map.
- The resolvers and renderers are pure functions that take no argv. That lets #71's layer 2 move them onto #119's step contract as `task/resolve-skills` and `task/select-lessons` without rewriting them. A resolver written in `rafa.config.ts` is a later issue; `SkillResolver` is exported for it.

## What can go wrong

- **The planner invents a skill name.** Refused by `plan validate` and by preflight before any session starts, naming the line.
- **The index grows past what a planner reads well.** It is capped at 8,000 characters, and the cut is announced in the index itself.
- **The tag arm offers skills that do not fit.** Expected; that is what a control is for. It keeps 3 at most, above the floor.
- **Lessons flood the prompt.** At most 5, and only blessed ones.
- **The arms leak into each other.** The resolver is recorded but never printed into the prompt. Arms alternate by whole plan, not by task.
- **The measurement is adjusted after the fact.** The protocol is committed before the first measured plan, and the doc's history shows any edit.
- **The collector breaks on a new log format.** It pins `SKILL_USE_CLI_VERSION`. A mismatch gives a `doctor` warning row, and the count reads `unknown`, never 0.

- The `task.skills` and `task.lessons` keys, `--skills-resolver=`, and `init` lines.
- Documentation: `context/workflow.md`, `context/effort-store.md`, the README section "Which agents and skills are involved", help snapshots, and `describe`.
- `changes:` notes and `release: minor`. Tick the README Roadmap line "The right skills reach the right task".

## Definition of done

- `plan create` on a fixture spec puts the index in the planner prompt, and a plan naming a skill no tier holds is refused by `plan validate`, naming the line.
- One fixture task dispatched under `planner` and under `tag` produces sections in the documented format. The test compares the format of both, and each dispatch row records its resolver and what it offered.
- A blessed lesson whose `artifact` path the task names is in `## Lessons from earlier tasks`. One whose path and trigger do not match is not.
- The collector counts the `Skill` calls in the recorded fixture log, in the main thread and in sidechains. The table holds nothing from the log beyond names and counts.
- `docs/skills-measurement.md` is committed with the protocol, the reading decided in advance, and the "before" table measured by backfill. The per-arm "after" readings are taken as the protocol states, using #24's report.
