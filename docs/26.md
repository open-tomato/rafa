## What you get

rafa resolves skills, agents and lessons in one fixed order, **project → rafa → user**, and a loop session receives exactly the winners. rafa ships its core roster in its own tier. On a new project `rafa init` copies nothing into `.claude/`, and a plan routes to `loop-implementer` on any repository. A project changes a default without editing it. It turns an item off, or pins which tier serves a name, in config: `.rafa/config.yaml` today, and after #118 `rafa.config.ts` with the same keys. A TypeScript project gets `ts-symbols` and its skill from the rafa tier without installing anything.

This is the fix #127 points to ("the gap #26's rafa tier closes for good"). The PR carries `Closes #127`.

## Starting position

- **Tiers exist only as path arithmetic.** `SKILL_TIERS = ['project','rafa','user']` is in `src/schema/tiers.ts`. The rafa tier is `skills/` beside the running `cli.js` (`bundledSkillsDirectory`), plus `agents/` there too (`bundledAgentsDirectory`, `src/inventory/trees.ts`). Nothing fills it: the `build` script copies `PROMPT.md`, `plan-prompt.md`, `dev-planner/SKILL.md`, the repair plans and the spec template into `dist/`, but no `skills/` or `agents/`. From a checkout the rafa agents directory is `src/agents/`, which already holds TypeScript (`roster.ts`, `vendorable.ts`).
- **The inventory shadows but never refuses.** `src/inventory/index.ts` orders sources `project, rafa, user, addon, plugin` and marks every later holder `shadowed-by:<source>`. `sourceVisibleToLoop` answers false for `rafa` and `addon:*`, because `claudeArgs` (`src/utils/claude.ts`) gives a session no directory of theirs. Its module note flags a known mismatch: a user item shadowed by a rafa item reads as not visible, yet the session loads it.
- **Sessions load the project only.** They run with `--setting-sources` from `loop.settingSources` (default `project,local`). `loop start`'s preflight (`src/start/preflight.ts`) refuses a plan that names an agent no loaded scope defines. `rafa agent vendor` copies from `~/.claude/agents` only. #127 is what that does to a new repository.
- **The routing table is prose.** It lives in `context/workflow.md`. The bundled `dev-planner` skill tells the planner to read it there, and no other project has that file.
- **Lessons have two scopes and no rafa scope.** `resolveInstinctScopes` gives `project` and `user`. rafa ships no lessons, by the decision recorded in `tiers.ts`.
- **Claude Code has per-session delivery flags.** Version 2.1.281 offers three flags that deliver items for one session without writing into the project:
  - `--agents <file>`: agent definitions under their bare names
  - `--add-dir <dir>`
  - `--plugin-dir <dir>`: items namespaced `<plugin>:<name>`

  Nobody has measured which of them loads a skill under its bare name with `--setting-sources project,local`.
- **Three agents to bundle came from a user-level install.** `tdd-guide`, `build-error-resolver` and `code-reviewer` each carry an HTML comment `Source: ~/.claude/agents/…`, and the original origin is not recorded. Nothing in this repository records provenance.
- **`ts-symbols` is not in this repository.** `src/plan/needs.ts` knows it only as the program on the TypeScript row (`def`, `refs`, `type`, `outline`, "over the TypeScript language service").
- **No config key covers these items.** None of the 30 keys in `SETTINGS` (`src/config-schema.ts`) touches skills, agents or routing.

## Design

### Resolution

- **One pure resolver.** `resolveTiers(rows, settings) → Resolution` in `src/tiers/resolve.ts` works over the inventory rows. For each kind (`skill`, `agent`) and bare name it picks the winner in the order project → rafa → user. It counts only the tiers a session loads: `user` only when `loop.settingSources` includes `user`, and `rafa` unless `tiers.rafa` is `off`. Plugins and add-ons stay outside the three tiers, read as they are today.
- **Collisions are refused.** When the same kind and name appear in two loaded tiers, `loop start` preflight and `plan validate` refuse before any session starts. The refusal names both paths and the one config line that settles it (a pin, below). `rafa doctor` and `rafa skill|agent list` show the item as `state: collision`.
  - An item switched off does not collide.
  - Two holders whose files are byte-identical once rafa's `vendored by rafa` header is removed count as one item. The nearer one serves it, and `doctor` suggests deleting the copy. This covers projects that took #127's workaround, and this repository's own links (below).
- **Lessons.** The project scope comes before the user scope, and a record with the same `id` is shadowed by the nearer one. Two scopes holding the same trigger with different actions is a conflict for #25's table, not a case of shadowing. The rafa tier holds no lessons.

### Served, not vendored

- **What is served.** Before each task or wrap-up session, rafa copies the winners Claude Code would not load by itself into `.rafa/runs/<run>/served/`. Today that means rafa-tier items only: a user-tier item is never served while `user` is not a loaded source. The directory is handed to the session with session-only flags. Project items are left for Claude Code to load. Because only winners are passed, Claude Code's own precedence between flags never decides anything. Copies are used rather than links, so a `self-update` during a run cannot change what a running session was given.
- **The mechanism is fixed by a probe**, run as the plan's first task:
  - Agents go through `--agents <file>`.
  - Skills go through `--add-dir <served>` if, under `--setting-sources project,local`, a session lists a skill from `<served>/.claude/skills` by its bare name.
  - Otherwise skills go through `--plugin-dir <served>`. rafa then maps bare names to and from `rafa:<name>` wherever it prints or matches a name, so `skills=` in plans keeps bare names.
  - The result and the CLI version are recorded in `context/inventory.md` and pinned as `SERVE_CLI_VERSION`. A different installed version gives one `doctor` warning row, the way `PLUGINS_CLI_VERSION` does.
- **Rejected alternatives.**
  - Vendoring into the project's `.claude/`: it writes into the tree, and it silently turns a rafa item into a project item that goes stale on every upgrade.
  - Pasting skill bodies with `--append-system-prompt`: the skill stops being a unit a session can invoke, which is the thing #23 hands out and #24 measures.
- **Inventory changes.** `sourceVisibleToLoop` answers true for a rafa item that is being served, and the "user shadowed by rafa" mismatch disappears.
- **`ts-symbols` on `PATH`.** A session's `PATH` gets `<runtime>/bundled/bin` added at the front, through the spawn environment in `src/utils/claude.ts`.

### The rafa tier's first contents

- **Where the tier lives.** It moves to `bundled/{skills,agents,bin}` beside the entry: `src/bundled/` in a checkout and `dist/bundled/` in a build, copied by `build`. This ends the clash with `src/agents/`. `bundledSkillsDirectory` and `bundledAgentsDirectory` change with it.
- **Agents**, the routing table's roster plus the bug filer: `loop-implementer`, `doc-updater`, `tdd-guide`, `build-error-resolver`, `code-reviewer`, `qa-bug-reporter`.
- **Skills:**
  - `documentation` and `git-workflow`, which those agents name.
  - `dev-planner`. It is no longer a separate `cp`: the plan-format fallback reads it from the tier.
  - The `ts-symbols` skill.
- **Every bundled item passes the checker.** A test runs `checkDirectory` over `src/bundled/skills`, and the agent check over `src/bundled/agents`, so a broken bundled item fails CI and never ships.
- **Provenance.** Each bundled item carries `provenance:` in its frontmatter. The value is either `first-party` or `{ origin, license }`. Before they ship, the three agents with `Source: ~/.claude/agents` are traced:
  - third-party → an `origin` and `license`, plus a NOTICE entry;
  - untraceable → rewritten as first-party, or left out of the tier and out of the default routing.
- **This repository keeps working in interactive sessions.** Its own `.claude/agents/<name>.md` and `.claude/skills/<name>/` for the bundled items become links into `src/bundled/`. They are byte-identical, so they are not collisions.

### Routing as data

- **`routing` becomes a setting.** It is a map from task shape to agent, and rafa's defaults are:

  | Shape | Agent |
  | --- | --- |
  | `prose` | `doc-updater` |
  | `tests` | `tdd-guide` |
  | `repair` | `build-error-resolver` |
  | `review` | `code-reviewer` |
  | `implementation` | `loop-implementer` |

  The two `user-level` rows (`cleanup` → `refactor-cleaner`, TypeScript review → `typescript-reviewer`) leave the defaults. They move into this repository's own `.rafa/config.yaml`.
- **The planner reads the table from a slot.** `plan-prompt.md` gains a `{ROUTING}` slot rendered from the setting. `dev-planner` points at the slot instead of `context/workflow.md`. The table in `context/workflow.md` is generated from the defaults, the way #119 generates its guard table.
- **Every row must resolve.** An `agent=` that `resolveTiers` cannot resolve still refuses at preflight and at `plan validate`. A `routing` row naming an agent that does not resolve is a load error.

### `ts-symbols`

- **Where it lives.** The CLI and its tests are imported into `src/tools/ts-symbols/` and built to `dist/bundled/bin/ts-symbols`. Its skill goes to `src/bundled/skills/ts-symbols/`.
- **Decided: it uses the project's own `typescript`, and `typescript` does not become a runtime dependency.**
  - How it resolves: from the project root, the way `tsc` would.
  - When there is none: it exits 3 with `no typescript under <root>: add it to the project`, and the skill says the same.
  - Why not a dependency:
    - #118 makes `@open-tomato/define-config` (zero transitive dependencies) rafa's first runtime dependency.
    - `typescript` is a 20 MB-class install that every TypeScript project already has.
    - The project's copy is the compiler its code was written for.
- **`plan needs` and `doctor --deep`** read the bundled program as present on the TypeScript row.

### Config, shaped for #118

Four keys join `SETTINGS`. Each is shaped so that #118's merge (maps merge by key, `false` removes, lists replace) applies without a special case:

| Key | Value | Default |
| --- | --- | --- |
| `tiers.rafa` | `on` or `off` | `on` |
| `tiers.skills` | map: name → `false` or a tier | `{}` |
| `tiers.agents` | map: name → `false` or a tier | `{}` |
| `routing` | map: shape → agent | the table above |

- **`false` turns the item off in every tier.** For skills, Claude Code's `skillOverrides: off` is still read as it is today. Agents have no equivalent in Claude Code, so this key is the only switch for them.
- **A tier pins which holder serves the name.** This is the one declared collision. It is also what #57's refine writes, in place of its proposed `overrides:` frontmatter key; `origin_hash` stays in the file. #57 is amended when it is re-opened.
- **`SETTINGS` gains one map reader** (name → value) for the three maps. `init` writes each key commented at its default.
- **All four keys are allowed at every layer.** A user-level pin naming a tier the project does not load is warned, not refused.

```yaml
# .rafa/config.yaml today
tiers:
  skills: { react-query: false, documentation: project }
  agents: { tdd-guide: user }
routing: { cleanup: refactor-cleaner }
```

```ts
// rafa.config.ts after #118: the same keys, typed
export default defineConfig([defaults, {
  tiers: { skills: { 'react-query': false }, agents: { 'tdd-guide': 'user' } },
  routing: { cleanup: 'refactor-cleaner' },
}]);
```

### Third-party sources: a stub

- **`provenance` is an optional frontmatter field on skills and agents.** The checker reads its shape: `first-party`, or `{ origin, license, reviewed? }` where `reviewed` is `<who> <YYYY-MM-DD>`.
- **Unreviewed third-party items are not served from the rafa tier or from add-ons (#29).** An item there whose provenance is third-party and has no `reviewed` is not served, and `doctor` lists it. Project items are reviewed through the project's own pull requests. User-tier items are the user's own install, so a missing provenance on one is a `doctor` note and never a refusal.
- **Out of scope:** no fetch, install or registry. That is #29.

## What can go wrong

- **The probe finds no way to load a skill by its bare name.** Skills are served through `--plugin-dir` with the `rafa:` mapping. One test covers each path, selected by the recorded probe result.
- **A user with third-party agents at user level turns on `user` and gets a collision on `tdd-guide`.** The refusal names both paths and the pin (`tiers.agents: { tdd-guide: user }` or `rafa`). `doctor` lists every collision at once, so settling them takes one edit.
- **A project that took #127's workaround now holds copies of bundled items.** A byte-identical copy is one item, not a collision, and `doctor` offers to remove it. An edited copy is a real collision and needs a pin, which is the point.
- **An upgrade changes a bundled skill a project relies on.** The change appears in the changelog's `changes:` notes. `skill list --source=rafa` shows the runtime version it came from. A project that wants the old text copies it and pins it with `tiers.skills: { <name>: project }`.
- **A bundled agent and the default routing drift apart.** A test resolves every default `routing` row against the bundle.
- **Claude Code changes a delivery flag.** `SERVE_CLI_VERSION` catches it with a `doctor` warning row, and the probe is re-run.
- **A bundled item turns out to be someone else's work.** The provenance trace comes before shipping, and an untraceable item is not bundled.
- **Key sprawl.** Four keys. Each one replaces a literal: the prose routing table, and the vendoring `init` would otherwise need.

## Definition of done

- In a scratch repository, a skill planted in each tier resolves project → rafa → user. Under `--setting-sources project,local`, the user-tier skill does not resolve at all.
- The same skill name in the project and rafa tiers makes `loop start` refuse before any session, naming both paths and the pin. With `tiers.skills: { <name>: rafa }` the run starts and the session is served the rafa copy.
- On a new repository after `rafa init`, with nothing under `.claude/`, `plan create` routes a task to `loop-implementer` and `loop start` dispatches it. `git status` shows nothing written under `.claude/`.
- A session in a TypeScript project with `typescript` installed, and no user-level copy of the skill, resolves the `ts-symbols` skill from the rafa tier, and `ts-symbols outline src/a.ts` answers. With `typescript` removed, the tool exits 3 with the named message.
- `tiers.agents: { tdd-guide: false }` makes `plan validate` refuse a plan that routes a task to `tdd-guide`.
- `rafa skill list` shows the bundled skills as `source: rafa`, `visibleToLoop: true`. Every bundled item passes the checker in CI and carries `provenance`.
