# Progress notes

- This repo (`open-tomato/rafa`) is a single-package bun repo: `package.json`,
  `src/`, `scripts/` at the root, no `packages/` directory and no workspace
  boundaries. Agent/doc files ported from the sibling
  `~/projects/agentic-research` (a bun-workspaces monorepo) must have every
  `packages/`, workspace and monorepo reference rewritten away.
- The plan schedules `.claude/skills/progress-hygiene` for deletion in a
  later stage ("Structured task report"), so don't treat its current
  presence as permanent when writing docs that reference skills.
- `rm -r`/`rm -rf` is blocked by this sandbox's Bash permission layer
  regardless of target path, /tmp included. To clear a directory, `mv` its
  contents to a scratch directory; to copy a directory's contents into an
  existing one, use `cp -R src/. dest/` (trailing `/.`).
- Relative imports under `src/` use `.js` specifiers for `.ts` files (e.g.
  `from './utils/claude.js'`) — normal TypeScript ESM style that bun/tsc
  resolve to the `.ts` source; leave them as-is when moving or repointing.
- Porting vitest to `bun:test` is a pure module-specifier swap for
  `describe`/`it`/`expect`/`beforeEach`/`afterEach`/`beforeAll`/`afterAll`.
  `vi.spyOn(...)` becomes `spyOn(...)` (same signature) and
  `vi.restoreAllMocks()` becomes `mock.restore()` (restores every spy at
  once); `bun:test` also exports a `vi` alias, but this repo prefers the
  native names. Verified: `spyOn(console, 'log')` behaves as under vitest —
  a `process.stdout.write` patch does NOT see `console.log` output — so
  "spy on console, not stdout" still applies verbatim.
- Bun's test runner resolves a bare `'vitest'` specifier to its own
  `bun:test` even with no `vitest` package installed, so `bun test` passing
  is NOT proof a port is complete — grep for the literal `from 'vitest'`.
- `tsconfig.json` excludes `**/*.test.ts` from `bun run check-types`
  (`tsc --noEmit`); its comment points at `.specs/test-type-checking.md`,
  which doesn't exist in this repo yet. So an editor diagnostic inside a
  test file (e.g. `bun:test`'s `toEqual()` overloads rejecting a
  `readonly T[]` vitest accepted) can appear without ever reaching the gate
  — confirm against that command before treating it as a build break.
- Some TSDoc still gives rationale tied to vitest running the suite under
  Node while the real spawner is `Bun.spawn` (`src/utils/claude.ts`,
  `src/utils/claude.test.ts`: "the root suite run[s] vitest under node";
  `src/effort/store.ts`: "under vitest on NODE"). The suite now runs under
  Bun, so that rationale is stale, but a literal "vitest" → "bun:test" swap
  would be wrong too (it no longer runs "under node" either) — a doc task
  should re-derive the rationale rather than search-and-replace it.
- Not every `tools/ralph` string inside `src/` is a path to repoint. Only
  genuine path literals (TSDoc file references, `new URL`/`readFileSync`
  targets, CLI usage examples) belong at `src/`. Leave test fixture text
  that merely quotes one, especially when a later assertion pins its LENGTH
  (`src/tests/commit-refusals.test.ts`'s 181-character `LONG_TASK`), and
  never rewrite fixtures representing ANOTHER repo's file
  (`src/tests/agents-split-accounting.test.ts`'s `RESIDUE` snapshots the
  sibling's own `AGENTS.md`, which legitimately names `tools/ralph`).
- When a file holding a `new URL('../../foo', import.meta.url)` base moves,
  recount the `../` depth from its NEW location, not just the path literal
  it appends: a `src/<subdir>/*.test.ts` reaches the repo root with
  `../../`. A wrong depth need not throw — `../../../` from there lands in
  the parent `open-tomato/` checkout, which has its own `packages/`,
  `AGENTS.md` and `.gitignore`, so guards read the wrong tree and still
  pass. Print the resolved absolute path once and check it against `pwd`.
- This repo has no `packages/`, so an unguarded
  `readdirSync(join(root, 'packages'))` only throws once `root` really
  resolves here — a wrong root masks it, and a passing run proves nothing.
  Guard every such read with `existsSync`, as `findAgentsMaps` in
  `src/tests/context-page-imports.test.ts` does.
- `.githooks/pre-commit` (wired by `core.hooksPath=.githooks`) already runs
  `scripts/control-byte-gate/control-byte-gate.ts --staged`. When a task
  says to "align" a file, check its current content first; it may already
  satisfy the target and need no edit.
- `bunx eslint .` fails at startup with `ERR_MODULE_NOT_FOUND: Cannot find
  package '@eslint/js'`: `node_modules/@eslint` doesn't exist although
  `@eslint/js` is in `devDependencies`, i.e. `bun install` hasn't run since
  it was added. It needs a `bun install`, not a config edit — don't mistake
  it for a problem in `eslint.config.mjs`/`eslint.base.mjs`.
- `bun test` is green over the whole `src/` suite (656 pass, 1 skip, 0 fail,
  26 files under `src/` plus `scripts/control-byte-gate/`, 27 total) —
  confirmed stable across three repeat runs, under `--randomize` (default
  and `--seed=42`), and via the `bun run test` script; all exit 0. A grep
  for `expect.extend`, fake timers, `vi.mock`/`mock.module`, and
  `import.meta.vitest` across `src/` found none, so nothing in the ported
  suite depends on a vitest-only mocking feature bun:test lacks.
- The suite's one skip is the genuine "passes only under vitest" case the
  port needed to preserve rather than delete: `src/utils/claude.test.ts`'s
  `it.skipIf(HAS_BUN)('defaults to the real spawner', ...)` asserts
  `runClaude(prompt)` rejects with a `ReferenceError` naming `Bun` when no
  spawner is injected — true only when `globalThis.Bun` is undefined, which
  happens under vitest-on-Node but never under `bun test` (where `Bun` is
  always defined). It is intentionally guarded with `skipIf`, not deleted,
  and its file header documents why; `src/effort/collect.test.ts`'s
  `it.skipIf(isRoot)` is a different, unrelated environment guard (root vs.
  non-root file permissions) and is not a vitest-vs-bun case.
- `scripts/control-byte-gate/control-byte-gate.test.ts` still has a literal
  `import { describe, expect, it } from 'vitest'` — the only remaining one
  in the repo. It predates the sibling import (it was one of the 3 files in
  the pre-import baseline) and sits outside `src/`, so the "port every test
  file under `src/`" task never touched it; it uses only
  `describe`/`expect`/`it` with no vitest-specific API, so it is not a
  vitest-only-passing test, just an unported literal riding on bun's
  `'vitest'`-to-`bun:test` shim (see the entry above on that shim). Left
  as-is as out of this phase's `src/` import scope; a future task touching
  `scripts/` should swap this one specifier too.
