- `rm -rf` (and even `rm -r`/`rm -rf` on files under /tmp) is blocked by this
  sandbox's Bash permission layer regardless of target path. Use `mv` to a
  scratch directory instead of deleting when you need to clear a directory's
  contents, and prefer `cp -R src/. dest/` (trailing `/.`) to copy a
  directory's contents into an existing directory without deleting it first.
- The sibling `tools/ralph/` tree (48 files) uses `.js` extensions in its
  relative imports (e.g. `import start from './start.js'` inside
  `ralph.ts`/`rafa.ts`) even though the files are `.ts` — this is normal
  TypeScript ESM-style import convention (bun/tsc resolve `.js` specifiers to
  `.ts` sources) and should be left as-is when porting/repointing paths in a
  later task.
- `bun:test` is a drop-in for the `describe`/`it`/`expect`/`beforeEach`/
  `afterEach`/`beforeAll`/`afterAll` shape of vitest's API — porting those
  imports is a pure module-specifier swap (`'vitest'` → `'bun:test'`), no
  call-site changes needed. For `vi.spyOn(...)`/`vi.restoreAllMocks()`,
  `bun:test` has its own native names: `spyOn(...)` (same signature) and
  `mock.restore()` (restores every spy at once, the equivalent of
  `vi.restoreAllMocks()`). Verified empirically that `spyOn(console, 'log')`
  under `bun:test` behaves like vitest's console patch: a `process.stdout
  .write` patch does NOT see `console.log` output, so the "spy on console,
  not stdout" pattern used in this codebase still applies verbatim. Note
  `bun:test` also exports a `vi` compatibility alias (`vi.fn`, `vi.spyOn`,
  `vi.mock`, `vi.restoreAllMocks`, `vi.resetAllMocks`, `vi.clearAllMocks`)
  for a literal drop-in port, but this repo prefers the native `spyOn`/
  `mock` names over that alias.
- Bun's test runner internally resolves the bare `'vitest'` module specifier
  to its own `bun:test` implementation, even with no `vitest` package in
  `node_modules` at all — `import { describe, it, expect } from 'vitest'`
  still runs correctly under `bun test`. So `bun test` passing is NOT proof
  that every `vitest` import has been ported; grep for the literal string
  `from 'vitest'` to confirm a port is complete rather than relying on test
  failures to catch a missed file.
- This repo's root `tsconfig.json` excludes `**/*.test.ts` from
  `bunx tsc --noEmit` entirely (a comment there tracks burning this down in
  `.specs/test-type-checking.md`, which does not exist in this repo yet).
  Because of that, a per-file/editor TypeScript diagnostic inside a test
  file (e.g. `bun:test`'s `expect(...).toEqual()` overloads rejecting a
  `readonly T[]` where vitest's looser typing accepted it) can appear
  without ever showing up in the project's own `bunx tsc --noEmit` gate —
  confirm against that actual command before treating such a diagnostic as
  a real build break.
- A few TSDoc comments describe historical rationale tied specifically to
  vitest running the suite under Node while the real spawner is
  `Bun.spawn` (e.g. `src/utils/claude.ts`, `src/utils/claude.test.ts`:
  "the root suite run[s] vitest under node"; `src/effort/store.ts`:
  "under vitest on NODE"). Now that the whole suite runs under `bun:test`
  (i.e. under Bun, not Node), that specific rationale is stale, but a
  literal "vitest" → "bun:test" word swap there would be actively wrong
  (the suite no longer runs "under node" either) — left untouched as
  outside the scope of a mechanical import port; a later doc-focused task
  should re-derive the rationale rather than search-and-replace it.
- When a colocated drift guard (a test that does `new URL('../../../foo',
  import.meta.url)` / `readFileSync` to re-read another source file and
  assert a literal is still present in it) survives a file move, the `../`
  depth in its `new URL` base has to be recounted from the NEW file
  location, not just the path literal it appends. Two such guards were
  found stale after the `tools/ralph/` → `src/` move (`src/effort/
  classify.test.ts`'s `keeps every prefix live` case, and `src/utils/
  progress.test.ts`'s `repoText` helper) — both used a 3-level-up base
  (`../../../`) that was correct for `tools/ralph/<subdir>/*.test.ts` but
  needed to become 2-level-up (`../../`) for `src/<subdir>/*.test.ts`, in
  addition to updating the appended path literal itself. A guard whose
  base is wrong doesn't necessarily fail loudly — `progress.test.ts`'s
  case still "passed" pre-fix because it was silently reading an entirely
  different repo's `.gitignore` outside this repo's tree (the umbrella
  `open-tomato/.gitignore`), not this one; only re-deriving the correct
  depth and checking the actual content read exposed that it had been
  reading the wrong file.
- Not every literal string containing `tools/ralph` inside `src/` is a
  real path reference to repoint after the sibling-tree move. Distinguish:
  (a) genuine path literals (TSDoc file references, `new URL`/`readFileSync`
  targets, CLI usage examples) — these should be repointed at `src/`; from
  (b) test fixture content that merely happens to quote a `tools/ralph/...`
  string as example/planted text, especially when its exact LENGTH is
  pinned by a later assertion (e.g. `src/tests/commit-refusals.test.ts`'s
  `LONG_TASK` is commented as "181 characters" and used in truncation
  cases) — changing those risks silently breaking an unrelated pinned
  assertion and is out of scope for a mechanical path-repoint task; from
  (c) fixture content that deliberately represents ANOTHER repo's file
  (e.g. `src/tests/agents-split-accounting.test.ts`'s `RESIDUE` constant
  is a snapshot of the SIBLING `agentic-research` repo's own `AGENTS.md`,
  which legitimately still names `tools/ralph` since that repo wasn't
  touched) — never rewrite these.
- A wrong `../` depth in a `new URL(..., import.meta.url)` base doesn't
  just risk ENOENT — it can silently resolve into a live, unrelated
  directory and read/write against IT instead. `src/tests/
  routing-table-agents.test.ts` and `src/tests/context-page-imports
  .test.ts` both carried `new URL('../../../', import.meta.url)` for
  `REPO_ROOT`, which is 3 levels up from `src/tests/<file>.test.ts`
  (tests -> src -> repo root -> one too many) and landed one level
  above this repo, at `/Users/marcos/projects/open-tomato/` — the
  PARENT directory holding this repo as a sibling among several other,
  unrelated checkouts. That parent happens to itself contain a
  `packages/` directory and its own `AGENTS.md`, so the bug produced
  plausible-looking (wrong) results rather than a crash, until `REPO_ROOT`
  was corrected to `../../` (2 levels up, the established depth for any
  `src/<subdir>/*.test.ts` file per the earlier `classify.test.ts`/
  `progress.test.ts` finding above) and the reads landed in the actual
  repo, which has no `packages/` dir at all. When auditing a `new URL`
  path base, don't just check it resolves without throwing — print/log
  the resolved absolute path once and confirm it against `pwd`, since a
  wrong-but-existing sibling directory is the silent-failure case that
  matters most.
- A `readdirSync(join(root, 'packages'))` (or similar) call with no
  `existsSync` guard in front of it will not surface as a bug in this
  repo until whatever computes `root` is ALSO correct — this repo has
  no `packages/` directory, so an unguarded read only throws once
  `root` actually resolves here. Guard every `packages/`-relative
  `readdirSync` the same way `findAgentsMaps` in `src/tests/
  context-page-imports.test.ts` already does (`existsSync(packages) ?
  readdirSync(packages) ... : []`), rather than assuming a passing test
  run proves the read is safe.
